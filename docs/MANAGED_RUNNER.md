# 后台测试执行器

> 0.17.3 原设计重审修正：当前聊天优先、先分号后自登录、无窗口浏览器及既有提速路径不变。共享探索、完整身份集合、公平保护、未知业务影响隔离和模块接单回执已接回当前链路。下文 0.16.22 等历史版本的“仅独占、无恢复预算、退出即回收”不再代表当前完整资源语义；详见 [逐项对照与边界](CONCURRENCY_RECONCILIATION.md)。这些修正不恢复逐请求远程核验、登录前置审批或每步重复检查。

平台负责分任务、分账号、回收和排队。Codex 负责登录、理解页面、执行测试和记录结果。

## 安装与启用

执行机支持 Mac 本机或 Linux，均需要 Python 3.11+。Mac 使用原生 Codex App Server、Seatbelt 隔离和本机 Chromium，不需要 Linux 虚拟机或 Docker。Linux 继续使用同机 Docker 后端。浏览器默认无窗口运行，登录由执行 Codex 完成；Web 平台不安装浏览器，也不提供 Docker socket。

在执行机检出本项目已发布版本后执行：

```sh
python3 -m venv .runner-env
. .runner-env/bin/activate
python3 -m pip install '.[runner]'
python3 -m playwright install chromium
api-test-runner doctor
```

Mac 的 `doctor` 在不启动模型轮次、不访问业务系统的情况下，检查文件/网络/子进程隔离、Codex 登录核验、初始化及动态工具线程、进程停止和重启，以及 Chromium 实际启动。失败时不注册执行容量。`--backend auto` 自动选择 Mac 或 Linux；`--codex-bin` 可指定本机原生 Codex 二进制（不能是 npm/shell 包装脚本）。默认优先查找桌面应用附带 CLI；同一次连接固定其 SHA-256，应用升级后须重启连接并重新核验，不能热切换未验证协议。

Linux 还需执行 `python3 -m playwright install --with-deps chromium` 和 `docker build -t api-test-codex:0.162.1 deploy/managed-runner`。

使用该执行机本人已登录 Codex 的 `auth.json`。平台不获取 Codex 登录凭据；各模块仅绑定同一个明确指定的模型认证文件，让 Codex 的文件认证后端共享刷新结果；不为每个模块复制刷新令牌。认证刷新会更新该文件，普通聊天历史和其他配置不提供给执行模型。若原 Codex 使用系统凭据库，按官方认证文档导出/配置文件存储并登录；不要把凭据粘贴到聊天、命令行参数或仓库。

1. 平台 `/orchestration` → 执行连接 → 生成连接码。
2. 运行 `api-test-runner pair --url http://192.0.2.20:18089`，按终端隐藏输入提示输入连接码。
3. 运行 `api-test-runner run --codex-auth /私有目录/auth.json`。`--model` 可明确模型；未指定沿用 Codex 默认。支持 ChatGPT 登录，不要求额外购买 API Key。
4. 在项目中登记账号和可选密码。平台先为任务独占分配账号，执行 Codex 通过租约限定的 `account_credentials` 工具取用该账号密码，自行识别页面并登录，无需用户先手动登录或展开个人信息。
5. 普通测试不以预先识别租户和角色为门槛；实际执行核对登录结果及权限，验证码、扫码、二次认证或错误凭据才请求用户协助。没有密码时仍可复用已有登录态。新执行机上报 `simple_dispatch=1` 能力，旧执行机不会收到这类任务，升级执行连接后原队列自动继续。
6. 在原会话启动测试，或通过 MCP 提交任务。平台按空闲账号和执行器容量排队，Codex 可自行拆分任务。


`--root` 是全局参数，写在 `pair/run/status` 之前。目录默认 `~/.local/share/api-test-runner`，包含连接凭据、机器身份、派发日志、Codex 历史和浏览器存储，禁止放进 Git。目录只允许本机账户访问。一个 root 只运行一个进程；重新配对必须使用原 root。不同执行机需要独立配对，不能复制机器身份与运行中的状态目录。

```sh
api-test-runner --root /私有目录/执行连接 status
api-test-runner --root /私有目录/执行连接 run --max-browsers 12 --max-models 6
```

容量上限是执行机配置，实际准入还取决于可用内存、当前浏览器上下文和运行中的模型；不是每个项目固定几个任务。默认上限浏览器 16、模型 8，可根据机器配置调整；当前保守内存估算每浏览器 768 MiB、每模型 2 GiB。Linux Codex 容器单进程上限 2 CPU / 2 GiB，启动配置在 `managed_sandbox.py`。Mac 复用相同的动态准入估算和可配置容量上限，不声称 Seatbelt 提供 Docker 的 CPU/内存硬配额；它通过独立模型进程和禁止子进程来维持进程归属。这些是运行端初始容量配置，不改变用例范围或账号持有规则。

## Mac 后台运行

登录和测试浏览器均默认无窗口运行，不弹出 Mac 浏览器窗口或 Dock 图标；网页“查看浏览器现场”继续显示同一浏览器。旧 `--headless` 参数保留兼容，省略也不会打开窗口。已有 LaunchAgent 升级执行程序后自动采用此默认行为。

前台 `run` 保持终端运行即可。配对后也可显式安装当前用户的 LaunchAgent，退出聊天不会关闭执行连接：

```sh
api-test-runner service install
api-test-runner service status
api-test-runner status
api-test-runner service stop
api-test-runner service start
```

安装会保存当前 Python 环境的绝对路径；需使用持续保留的虚拟环境，不要删除它。服务在登录 Mac 后启动，退出登录后停止；休眠时无法继续执行，恢复后先结束旧执行进程，再按原任务进度排队续跑，不把休眠当作账号释放。连接日志位于私有 root/logs；LaunchAgent 位于当前用户的 Library/LaunchAgents/com.api-test-workspace.managed-runner.plist。已有服务不会被另一个目录静默覆盖。网页撤销执行连接仍优先于任何本机自动重启。

## 执行链路（0.16.22 起）

1. 原会话提交目标和范围，保存原用例编号、回归基线与历史。
2. 按队列顺序取得一个项目账号和可用执行器。账号独占，不要求预登录、身份核验、租户角色或共享规则。
3. 启动或续接该任务的 Codex。通过 `account_credentials` 取到分配账号的凭据，自己登录和操作无窗口浏览器。
4. Chromium 正常联网，包括重定向、流式请求和页面依赖。没有平台逐请求账本，也没有每次点击审批。定位失败或页面错误只返回给 Codex，不撤销整个任务。
5. 普通 `checkpoint` 保存进度，探索、执行、报告在同一任务中继续。`finish` 表示本轮结束；完成、明确受阻或主动交还均结束执行进程并关闭浏览器，然后回收账号。
6. 未完成任务主动交还后进入队尾，先让已经等待的任务取得账号。已受阻任务保留具体原因和原记录，继续操作仍使用原任务。没有清理审批、人工解锁或累计恢复预算。

原执行进程退出前不能把同一个账号交给另一执行者，这是防止账号并用的基本约束。断线时执行器停止自己的模型与浏览器，联网后重试同一回收请求；平台不把心跳超时误当进程已经退出。回收请求持久化并可幂等重试，不重放业务操作。

账号登录态按账号保存在本机私有目录，后续任务可复用；编辑或删除账号后清除失效缓存。浏览器关闭和账号回收不依赖登录态保存或报告发布成功。凭据不进入公开状态或报告。

完成任务与测试通过分开记录；未完成检查不能标为通过。旧未知操作保留原状态及历史标记，续跑时由 Codex 查看实际业务状态，避免重复提交，不把缺失回执改写为业务成功。

## 升级

先按标准 Jenkins 流程发布平台，再升级执行器到同一版本。新版执行器检查平台协议；旧版执行器不会领取新协议任务。原任务和账号数据兼容保留，不新建五个回归任务、不重置用例历史。

旧租约由其原执行机结束进程后通过新的回收接口交还；平台保留旧操作为历史，不要求再次逐项审批。历史协议接口仅供旧版本退出，新的执行链路不调用它们。

平台按 `docs/JENKINS_RELEASE.md` 发布。执行机安装对应 wheel 后重启原 LaunchAgent，配对信息、线程和用例继续复用。浏览器始终无窗口，不以连接在线替代实际浏览器操作和用例记录作为续跑证据。

0.16.23 将记录接口的具体校验原因返回给 Codex 自行修正，不回显请求内容或凭据。没有账号时自动任务仍留在后台队列，不再隐式切换到本地浏览器。正常 HTTP(S) 网页与跨域登录不经过审批；不接受本机文件或脚本作为导航地址。

0.16.24 补齐浏览器上传契约：`browser` 的 `upload` 接受 `parameters={selector,asset_id}`，取当前任务记录中的原测试文件并上传原字节。没有额外审批，不要求模型访问本机路径或重建原样本；账号和任务归属仍与现有分配一致。也可使用 `selector,filename,content_base64,content_type`。

0.16.25 使用 `thread/resume.excludeTurns=true`，仅接收续接元数据；原线程完整历史仍由 Codex 保留。避免正常长测试的多兆字节历史被控制通道整包回传而断开，不重建原线程，也不再遍历历史轮次尝试中断。原资产若仅记录通用二进制媒体类型，上传按文件名推断原生文件选择器的类型；显式 `content_type` 仍优先，文件字节保持不变。

用户继续未完成验证时，managed_control(action=resume,instruction=续测要求) 会让 coverage_complete=false 的已结束任务沿用原线程和报告继续；完成覆盖的任务保持结束。历史结果保留，不重跑已确认部分。

## 0.16.29 直接执行与容量修正

当前聊天通过 direct_test_session 控制原执行连接的无界面浏览器，执行连接不为 direct 租约启动 App Server。两条路线共享账号占用。默认 --max-models=0 / --max-browsers=0 表示自动，不再按每 2 GiB 推算一个模型。浏览器初始 768 MiB 估算会用实际子进程 RSS 峰值校准；显式配置上限保留。原文中固定 16/8 和每模型 2 GiB 的旧估算已被本条替代，不是 Codex 官方限制。启动、进展、失联、人工等待超时及恢复边界见 CODEX_EXECUTION_ROUTES.md。执行机须安装同版 wheel 后重启原服务，保留配对、任务与浏览器归属日志。
