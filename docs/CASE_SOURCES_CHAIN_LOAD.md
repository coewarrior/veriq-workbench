# 用例来源、业务链路与可选压测（0.11 首版）

在同一测试会话中，第二步选择用例来源，第三步执行，第四步查看报告。

| 用例来源 | 操作 |
| --- | --- |
| 执行自己的用例 | 导入 CSV / JSON → 核对请求与预期 → 执行；不调用模型 |
| 直接 AI 生成 | 选择 Codex / 已配置的模型 → 完整设计和生成 → 核对 → 执行 |
| 导入后 AI 补充 | 先导入 → AI 读取已有请求、断言和设计，追加遗漏场景 → 核对新增项 → 合并执行 |
| AI 生成后自己补充 | 先生成 → 导入或手动追加自己的用例 → 核对新增项 → 合并执行 |

切换方式不会删除用例。导入使用唯一 ID；重名返回冲突，不能悄悄覆盖。
用户用例保留来源标记和原预期；模型补充使用新 ID，未修改用例保留核对状态。
Codex 的替换提交也保留用户用例；修改用户原用例需通过网页明确编辑。

## 业务链路为什么需要

例如五子棋的“注册 → 登录 → 查询用户 → 清理测试账号”，查询依赖前面产生的身份。
资源接口的“登录 → 创建资源 → 提取 ID → 查询 / 修改 → 删除并确认不存在”同理。
单独请求不需要拼成链路；只有步骤有先后条件、共享身份或数据时才使用。

已有执行器原本支持变量、Cookie、Token 和清理；本版增加可见的链路预览与编辑入口。
在第二步点“业务链路示例”可查看不发请求的示意；展开真实用例，点“查看 / 编辑业务链路”可看到实际步骤。
多步骤用例支持上移 / 下移，单步骤隐藏排序按钮。高级编辑可修改 JSON，预览会提示有无修改，列出前后内容并展开变化步骤；保存后重新核对修改项。
首版是顺序链路，不包含拖拽画布、任意脚本、条件分支或跨用例共享全局变量。

- 同一条用例内按顺序执行，默认保留 Cookie；请求显式设置 `session: false` 时不复用。
- `extract` 可从 JSON、响应头或 Cookie 提取变量，后续请求用 `${变量名}` 引用。
- `variables` 的 `unique` 值每轮重新生成；`literal` 按用户填写的固定值使用。
- 步骤失败时跳过依赖的后续业务步骤，仍尝试已配置的后置清理。缺少清理所需变量时如实记录。
- 修改链路不会发送请求，历史报告和运行快照不变。

## 导入格式

首版支持 **JSON / CSV UTF-8**，单文件最多 4 MB。可下载模板，也可粘贴文本。
Excel 可以另存为 CSV UTF-8；本版不直接解析 XLSX、Word 或自然语言用例表。
JSON 支持多步骤链路；CSV 一行一个单请求用例。

CSV 字段：`id,title,method,path,expected_status,json,params,headers,assertions`。
也支持中文表头：编号、用例名称、请求方法、接口路径、预期状态码、请求体、查询参数、请求头、断言。
`json` / `params` / `headers` 为 JSON 对象；`assertions` 为 JSON 数组，CSV 中需正确转义双引号。
已有接口必须能按 operation_id 或 method/path 对应到当前接口文档。

```csv
id,title,method,path,expected_status
MY-001,读取健康状态,GET,/health,200
```

JSON 示例（请改成自己的真实接口和预期）：

```json
{
  "cases": [{
    "id": "MY-001",
    "title": "读取健康状态",
    "operation_id": "get_health",
    "variables": {},
    "steps": [{
      "id": "read",
      "request": {"method": "GET", "path": "/health"},
      "assertions": [{"kind": "status", "expected": 200}]
    }],
    "cleanup_steps": []
  }]
}
```

用户填写的断言作为用户预期保存，可追溯到导入文件；空白预期不自动补成 200。
导入文件中的 READY / 审核标记不直接生效；核对后才会执行。
“导出可导入 JSON”导出请求、断言、变量和清理步骤，可编辑后重新导入其他会话。
同一会话修改已有 ID 请使用链路编辑入口。

## 手动添加与删除

手动添加使用表单：先选择接口，填写用例名称、请求参数和预期状态码或响应字段。接口和预期不默认填写，不需要编辑整条用例 JSON；保存不会发送请求。请求体支持参数表形式的 JSON、URL 编码表单和原始文本。专门测试不带凭据的场景可明确选择「未登录 / 不带鉴权凭据」。复杂多步骤仍可在高级编辑中维护。

展开用例可删除；「已删除用例」中可恢复。删除不修改历史执行报告和用例快照，不覆盖其他用例或它们的核对状态。恢复时若已有相同编号，或相关接口/判断标准已变化，会提示冲突。

## 可选压测

侧栏提供独立「压测」入口（`/api-testing#load`）。选择已有测试会话后，主动勾选并设置虚拟用户数、时长、轮次和间隔，明确选择可执行用例，再启动压测。Codex 自动完成测试后可直接从此入口使用已保存的用例，无须进入第三步；任务完成或报告同步不会把用户带离压测页面。
普通“开始执行”不会启动压测，即使已勾选压测选项也一样。
每个虚拟用户顺序重放所选用例；每轮独立 Session，unique 变量重新生成，固定数据仍会重复使用。

本版复用功能测试引擎：最多 20 个虚拟用户、300 秒、总计 5 万次计划 HTTP 请求，所有虚拟用户合计最多 1 万轮。
这是当前单机运行容量，适合先体验并发验证；不提供分布式发压、阶梯加压或目标 RPS 控制。
到时或点停止后不再新增轮次，在途链路与清理结束后出报告。
出现连接异常或清理失败时停止新增轮次，并保留失败样本。

报告独立保存，不替换普通功能测试报告；同一标签打开，可返回测试台。
展示请求数、平均 RPS、P50 / P95 / P99、未通过比例、响应状态码、轮次汇总和最多 5 份失败样本。
请求统计包括前置、业务和 HTTP 清理；失败以用例断言和连接结果判断，预期的 400 / 409 不算失败。
平均 RPS 包含运行与清理等待时间；分位数只统计收到响应的请求；时间表按轮次完成时点汇总。
受执行器和本机资源影响，这些数值不能直接当成被测服务的极限容量。

## 验证

自动检查覆盖四种来源、模型补充上下文、MCP 基线保护、导入冲突和编辑失效重审。
真实 HTTP 在本地临时资源服务验证 Token / ID 传递、多轮清理、停止和清理故障。
模型响应使用本地模拟，不消耗用户模型额度；未对共享业务服务执行压测。

### 压测图表与当前容量边界（0.11.5）

报告提供吞吐量、响应时间 P50/P95/P99、未通过比例的时间趋势，以及整体响应耗时和 HTTP 状态码分布。图表使用已保存的测量数据，可以离线查看；展开逐秒表格可核对数值。

新执行按每个请求完成时点采样，包含业务和 HTTP 清理请求；无请求秒的吞吐量为 0，但无响应秒不伪造 0 ms 耗时。末尾不足一秒的吞吐量按实际窗口折算。在线打开旧报告也会获得新图表，原始 JSON 和离线快照不变；旧版仅有按轮次完成时点汇总的请求数，不能据此还原真实逐秒响应时间。

20 虚拟用户、300 秒、5 万计划请求是当前内置链路回放引擎的软件边界，不是被测服务的实测容量。它使用线程池，复用完整功能执行器和临时报告，与网页服务共用进程。直接把上限扩大到一万会同时放大线程、会话、文件输出和校验开销，不能据此声明支持万级压测。

虚拟用户、同时在途请求和每秒请求数应分别测量。未来的大规模压测应采用独立的 JMeter CLI 或其他专业发压引擎，由网页管理任务与报告，并支持独立发压节点、逐步升压及发压机资源监测。是否需要分布式、能否稳定达到目标 RPS，需按请求复杂度、延迟、数据准备和节点实测结果确定。当前版本尚未接入 JMeter 或分布式发压。

### Apache JMeter 执行（0.12.0）

压测页可选择 Apache JMeter，测试台将已核对用例转换成 JMX 计划，调用独立 Java 进程执行，读取 JMeter 原生 CSV JTL 生成统一图表。无需云平台账号。新会话在引擎可用时默认选择 JMeter，但仍需主动开启、选择用例并启动。

支持请求方法、路径、查询参数、请求头、JSON/文本请求体、每轮唯一变量、字面量、JSON/Header/Cookie 提取、会话 Cookie；显式 `session:false` 使用独立空 Cookie 会话。支持状态码、状态集合、JSON 字段相等/存在、变量相等、响应头、Cookie 及常用 Schema 断言。Schema 支持类型、属性/必填、额外属性、数组元素/数量/唯一性、长度、数值范围、枚举、常量、allOf/anyOf/oneOf/not；未支持的关键字（例如 format）在执行前报出，不能静默忽略。

每个用例开始时重建变量与 Cookie 状态，业务步骤失败后跳过其后续依赖步骤，HTTP 清理继续执行。用户停止、到达时长或轮次上限后不再开启新轮次；清理失败停止新轮次。引擎超出链路超时宽限期仍不能退出时终止进程，并在报告中标记可能未完成清理。依赖本地 Python/MySQL 清理适配器的用例不能直接转成 JMeter，需先提供 HTTP 清理或独立压测数据方案。

参数：虚拟用户数、升压时间、持续时间（包含升压）、每轮间隔、所有用户合计的轮次上限。部署默认允许配置 1–10000 用户，可通过 `JMETER_MAX_USERS` 调整；这是接受配置的节点边界，不是已证明的吞吐量。实际容量应逐步实测。已通过本机隔离环境 32 用户、192 次真实请求、Token 链路与清理验收；没有对共享业务服务做容量测试。

在线报告区分引擎异常和断言失败，提供实际活跃线程、吞吐量、耗时和未通过比例图表。原生 JTL 和完整计划包仅会话所有者可下载，计划可能包含请求凭据；公开报告仍只提供脱敏结果。完整计划包包含 JMX、固定的 Groovy 转换脚本及参数文件，可用 JMeter 5.6.3 命令行复现。

JMeter 使用原生 HTTP 组件；服务器先核准目标解析并将地址固定到计划中，禁止跟随重定向，HTTPS 目标进行系统 CA 证书预检。JMeter 自身的 TLS 行为与功能执行器不完全相同，此集成不用于验证 TLS 证书策略。
