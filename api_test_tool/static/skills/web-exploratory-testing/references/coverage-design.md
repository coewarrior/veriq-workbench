# 覆盖设计与回查
## 当前平台全局范围（2026-10-26）

当前平台全局范围：多账号、双账号、跨账号及跨租户对照/隔离业务场景一律不测（用户明确排除多账号场景）。保留具体设计和已有真实结果；未执行项使用 not_run，not_run_reason 填写上述原因；UI cases.account_scope、API design.account_scope 使用 multi_account/cross_account/cross_tenant 明确范围。不算通过，不申请第二账号、不等待账号集合、不为其创建执行会话或续接，不另做替代测试。普通继续测试/重测不解除此规则。不同模块各用一个账号并发仍允许；单账号权限、匿名及其他适用风险覆盖保持。已有真实对象责任的必要清理和无需账号的报告仍按原授权及回收协议处理，不扩展业务测试。

此明确范围变更优先于下文历史多账号示例；既有隔离、授权、清理及回收协议仍保护历史现场，不授权发起新多账号业务。


## 1. 用原始依据确定业务范围

本文件是范围设计和遗漏回查的统一规则；执行速度、资源安排和报告格式不改变这里的范围。

先结合本轮目标、附件完整原文/表格及必要页面侦察，说明每个模块的业务对象、实际入口、关键功能/规则和业务终点。记录在现有 `coverage` 与具体用例中，不增加表单、审批或新协议。用户仅指定模块时覆盖模块内适用行为；明确指定流程、问题或选中用例时遵守该较窄范围。权限决定能执行什么，不能把未授权分支删出设计。

模块名存在歧义时，核对文档描述、真实入口和对象。资料中的简历问答/电话认证，不能因为名称叫“候选人认证”就改测求职者登录。页面上未找到入口，记录未找到的功能及查过的具体位置；不能用一个可访问的相近页面替代原目标。

新独立轮次（含明确新回归）复用当前有效的功能资料和规则，使用本轮新建的聊天并重新记录结果；同轮续测复用本轮真实聊天绑定、原结果和检查点。已有本轮模块计划或设计不代表历史轮次，重复接入也不重新建聊天。历史设计用于发现可能遗漏，按本轮范围、功能变化和真实重复核对后采用，不复制历史通过，不按旧条数凑数。新轮目标、附件和授权由协调者在启动时核对，执行者不重复完整启动审查。

新轮 `design_references` 是平台按同账号项目、目标 origin、原附件哈希提供的历史设计候选。读取与本模块相关来源的 `get_ui_design_reference` 全部分页，先对照当前原资料再采用。旧轮更少或更新不代表覆盖更全：比较具体来源分支，保留仍适用的独立输入和状态；历史标题/规则也可能有误，由 Codex 修正。现有 coverage/review_notes 按“来源 project_id/source_case_id → 本轮 case_id，或不适用/合并重复的具体依据”记录差异。历史只传设计，不能继承通过或把旧条数当配额；首批可以直接执行，收尾补齐尚未映射的范围。

## 2. 已知范围保持可见，详细设计按批推进

范围笔记先保留已知功能及未验证问题，再按共享初态分批写具体用例并执行；不要求所有详细用例写完才开测。已有设计直接复用，新发现追加同轮。仅设计任务不等待执行账号；必要页面无法查看时先依据资料设计，并注明待核对内容。

设计时先按 [用例名称与字段写法](reporting.md#用例名称先说明验证点) 写清“场景／操作 → 预期行为”，每条围绕一个独立业务判断。公共准备归入前置或准备说明，数据、步骤和预期中的对象须一致，执行纪律不重复写入前置。

用例包含具体前置、完整输入、编号步骤、可观察预期、依据和执行方式。规则未明确时保留待确认问题或条件化预期，不编造阈值、控件和入口。需求原文与 AI 解释分别记录；实际实现不是符合需求的证明。通用资料用于发现风险，不替代产品验收规则。

不同初态、有效/无效输入、边界值或独立失败结果分别保留可追溯用例 ID。一个端到端正常链路可跨多次点击，不机械拆点击凑条数；多个独立规则也不能共用一个笼统结论。用例可以共享准备、工具调用和证据，每条结果仍独立。

具体落盘方式：每个独立场景一条 `cases`、一个稳定 `case_id`、一组明确的初态/输入/预期/结果；同一场景的连续步骤和必要断言才使用该条的 `checkpoints`。例如阈值 79、80、81 分别三条，自动开关关闭和手动触发另列；通过、拒绝、待人工、失败、过期等不同初态分别列；键盘、窄屏、匿名、跨租户不能拼成一个场景。共享前置、相同阻塞或一次工具批量操作都不合并这些用例。发现原设计混装时在本轮拆出独立 ID，保留原记录和来源，不把旧综合结论复制给新条目。

拆分仅有设计或前置阻塞、尚无执行事实的旧聚合时，先保存独立替代用例，再在旧条目显式填写 `superseded_by:[替代case_id]`（也可同批保存）。原条目和历史保留在 `superseded_cases`，不重复进入活动用例计数；不能用这个字段隐藏已有通过、失败、部分执行或历史执行事实。原始范围与替代场景仍须逐项核对，结构关联不证明覆盖充分。

按实际功能选择等价类、边界值、场景、错误推测、判定表、状态迁移或约束成对组合。包括适用的正向、逆向、边界、安全、权限与隔离、取消/重试/重复、持久化、异常恢复和跨入口一致性；不机械逐格套表，也不把此列表当上限。边界说明单位和包含关系，组合缩减不省略关键高风险组合。

例如完整上传功能要区分有效文件及内容可用、格式限制、空/损坏文件、实际大小边界、多文件与失败恢复等适用规则；测了 EXE 拒绝和损坏 PDF，不能代替有效 PDF 解析。只把上传作为某条明确限定流程的前置时，不强行扩大成上传专项。窄屏模拟不等于真机，页面不溢出不等于移动端关键操作通过。

短文本写完整输入；文件型数据提供真实可复现文件、精确格式/大小、构造方式和用途，上传为 fixture 绑定用例。本地文件名列表不能代替交付数据。同等价类无意义换值无需重复；不同格式、边界和业务判断不能因共用文件而合并。

## 3. 缺条件时分开处理设计与执行

共同前置在同目标、环境、角色和数据条件下核实一次并复用。能在当前授权内生成样本、创建对象、切换状态或完成关联步骤的，先完成准备；不能把“还没准备”直接当阻塞。无法补齐时，将已知独立下游用例分别关联该依赖并保存缺口，继续其他可执行分支。

共同故障应说明实际检查位置、时间、响应及受影响用例的依赖关系；不把未操作下游写成每条都复现了故障。登录服务异常、管理端角色/账号配置、设备、样本分别关联，不能批量套一个原因；无需该前置的匿名、输入边界及其他独立分支仍按实际条件执行。同轮出现明确恢复证据时，Codex 核对受影响的原阻塞与剩余断言，更新对应诊断并走正式续接；原观察和已完成结果保留，不自动重跑、不加定时轮询。平台的 review_remaining 只是提醒复核，不替模型改判，也不要求已确认仍受阻的路径重复尝试。

所有类型条件均使用这条恢复路径：账号、权限、文件、数据、服务、观察能力、支付、工具、网络和其他实际依赖，以及规则答案、用户授权或人工步骤。`execution_plan.recovery.pending_refs` 保留原 `case_id`、可选 `checkpoint_id` 及真实未完成条件；`review_required_refs` 表示需要模型复核，补充数据仍需验证，不等于依赖已就绪。逐检查点核对已解除条件与剩余断言，独立分支不被另一分支或已完成检查点的旧依赖挡住。无结构化原因时先核对原阻塞事实并补充准确关联，不按错误文案或故障码猜测恢复；检查点 `depends_on` 仍按原前序成功语义，不能与资源阶段完成依赖混用。

空候选列表只能验证空态，不能覆盖非空详情、简历、分析、收藏、切换和状态迁移。资料已明确的分支仍分别保留设计；不能将它们压成一条“详情链路受阻”。如果这些功能本身尚未知，保留待探索问题，不能虚构完整设计或声称不存在。

AI 无法可靠完成但目标内有价值的场景，保留可交接的人工设计和所需条件。`pending_action` 是具体授权或人工步骤，`pending_rule` 是判断规则未知，`blocked` 是已核实的客观依赖缺失，`not_run` 是尚未执行；不能互相代替。准备、可调度和实际就绪不是同一事实。

逐项写真实原因与下一步：授权不足用 `pending_action + action_type=authorization`，引用当前授权未覆盖的具体操作；确需登录/提供账号/人工步骤用 `pending_action + action_type=manual_step`，`action_required` 写用户要做的一件事；规则未知用 `pending_rule` 写待确认规则；已核实且用户无法就地补齐的外部依赖用 `blocked`，写检查证据；当前授权内尚未准备的数据仍是 `not_run`，由执行者准备后继续。有多个原因时逐项列出原因、影响用例 ID、已做的准备和下一步，不能统一归入“权限不足”。工具中断单列工具事实与恢复过程，业务已完成/未完成的断言分别保留，不因超时改判业务失败。

真实共同工具/网络故障使用既有 `cases.dependencies` 与 `record_ui_dependency_check`：`kind=tool/network`，`scope` 写明本轮实际运行时/隔离上下文或网络路径的非秘密标识，同一个原因只检查并保存一次，关联具体独立用例。不同浏览器不能仅因相同报错共用工具原因；授权、数据和业务依赖分别关联。`blocked`/`ready` 只更新该原因的诊断，不自动修改用例或检查点，也不阻断资源候选。Codex 判断条件变化后哪些结果需要更新，显式保存；其他原因、原阻塞历史和已执行事实保留，不自动将已判定的用例重做。回执 `blocking_summary` 同时说明原因数、受影响用例数和未关联结构化原因的阻塞条目；旧文案需结合本轮恢复证据明确修正，不按字符串推断、不批量清空。

“测不了就不测、不提问、不阻塞其他测试”按以下实际条件执行，普通资源等待不归入无法测试：

| 已知事实 | 当前动作 | 仍需保留 |
| --- | --- | --- |
| 非排除、非停止的账号排队或共享转独占；回执明确资源等待（如 release_required） | 继续当前合法独立项；到边界按原 yield 临时交还，结束本回合等原事件 | 原节点/阶段、待执行用例和顺位；不以 completed 提前结束模块；stage_ready=false 先看具体原因 |
| 当前授权内尚未准备的合成样本 | 先尝试实际可用的准备路径；准备需要独占时按上行处理 | 未执行设计；准备不等于断言通过 |
| 已核实无可用入口/外部条件，或操作超出授权且用户要求不问 | 逐项记录证据和确切原因，跳过相关分支，继续其他项 | 独立设计和真实缺口；可以交付部分报告 |
| 用户明确停止本轮 | 停止业务、取消排队续接、按原退出流程交还 | 已有结果及未完成范围；不自动恢复 |

只读核对使用当前账号已获准访问的数据，不把“禁止修改既有共享数据”扩大成禁止读取，也不要求每个只读样本必须本轮创建。写入、状态迁移和清理才需要确认可修改范围及对象归属。成功链路缺样本不自动阻塞独立的空值、无效链接、匿名拒绝等场景；分别核实其真正前置。真实缺入口或无法安全确定对象时如实跳过，不猜造可达路径，不扩权。

相同条件失败已有确定证据后不重试；条件真实变化才续接。普通工具异常保留现场和未保存观察，处理对应错误；不重新执行业务来解决保存失败。平台执行计划只安排已登记用例，不能证明设计完整；计划进入 report 时仍须核对已知范围中的遗漏。

## 4. 在有意义的节点回查

执行者在新事实改变范围时更新笔记；首批设计和模块收尾复用现有记录回查。协调者的介入时机见 [模块协调](coordinator.md)，不每条调用评审或唤醒模型。

回查顺序是原资料/功能/规则 → 用例与独立判断 → 本轮证据与结果。不能从已有用例标题反向生成一份清单来自证完整。检查：业务方向是否正确；哪些范围项没有用例；独立分支是否被大标题吞掉；剩余项是未准备、真实阻塞还是规则未知；是否漏了可执行的重要分支。

在现有 `coverage` 中按原资料来源登记范围，`case_ids` 关联独立场景；有结构化需求时沿原 `save_requirement_design`/`requirement_ids` 关联，不把清单空白当作没有需求。模块收尾的 `review_notes` 保存逐项核对结果，每行包含：**原目标/文档章节与规则 → 独立状态或输入分支 → 用例 ID（无用例明确写缺设计）→ 本轮证据及未验证点 → 缺口类别与下一步**。尚无设计的范围也必须在这份核对中出现；只有统计、失败列表、“已回查”或一段全局阻塞说明不算核对。复用未变的来源与证据，仅补变化，不重新操作已验证业务。

原生收尾的 `review_state.scope_review_file` 是本地核对材料，包含完整缓存用例和已登记范围及分开的剩余状态；它没有读过原文，`semantic_review_complete:false` 不是执行失败，而是明确不能由工具代做语义核对。执行者对照原始资料补齐核对结果后用既有 review/complete 保存 `review_notes`。没有资料的项注明未知，不能自动编造完整率；这不增加保存、资源交还或部分报告发布门槛。

已有且未变的证据直接复用，只补具体缺口。仍能推进的重要用例继续执行；用户明确停止、范围/时间边界已到或客观条件不可补齐时，保存实际结果、完整已知剩余范围和原因，交还资源并交付部分报告。用户无需审批用例才能继续，也不因缺口禁止保存和发布。

已登记用例完成比例只衡量这些用例，不代表全部业务覆盖。模块结束与目标全部验证分开说明；缺失功能不因没进入分母而消失。范围变化说明来源和具体差异，不用固定数量或规定分钟数判断充分性。
