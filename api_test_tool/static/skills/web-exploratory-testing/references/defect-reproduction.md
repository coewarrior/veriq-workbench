# 可独立复现的缺陷步骤

面向没有参加测试的开发写缺陷。对照实际操作、输入和证据逐条整理，不能让开发猜“本轮”“受控状态”或测试者省略的路径。失败用例的 steps 会直接进入缺陷草稿，因此保存失败结果时就要补齐；发布前再核对一次。

- 前置条件仅保留这条缺陷实际依赖的环境、角色/权限、已有对象与初态，说明如何准备或核对。不复制“可投/未登录/资料缺失/卡点等状态”这样的所有分支模板。
- 测试数据给出对象名称、必要标识、具体输入和文件引用。凭据脱敏并说明获取方式；文件应能在报告中获取。键盘按键是操作，不能用一串按键名代替数据和步骤。
- 步骤从可定位的 URL、页面及入口写起，按实际顺序编号，一步一个主要动作。写清控件名称及位置、输入什么、选择哪个对象、等待什么可观察状态，以及在哪里观察故障。弹窗作为前置状态时，也要说明实际打开它的路径。不要求固定步数，简单操作不用凑数。
- “沿用已登录账号”“当前测试账号已登录”不能单独作为步骤。必须写打开哪个 URL、通过页面哪个账号名/头像/登录标识确认会话、点击或选择哪个控件和对象、等待什么状态；选择、刷新、核对拆成不同编号。原始记录未保存的按钮名或账号标识要直说缺口，不凭经验补写。
- AI 对话缺陷保留真实发送原文和会影响结果的上下文；不能把“要求开始投递”当作完整输入。批量操作列出具体选中对象和数量；依赖顺序的选择保留顺序。
- 键盘问题写清打开弹窗的触发控件、起始焦点、实际按键顺序、关闭方式和关闭后的焦点位置。只有用过的关闭方式才是复现路径，不能把 Enter、Escape、鼠标关闭视为同一次验证。焦点需有实测依据，例如 document.activeElement 的标签和可读名称；测量时不能因为打开开发者工具或点击页面改变焦点后再冒充原始结果。
- steps 写到故障出现的位置。expected 与 actual 对应该步分别说明“应该发生什么”和“实际发生什么”；故障后换入口、绕行成功、恢复与复测放在 actual 中单独交代，不插入原始触发链，也不能把未执行的登录、补资料等分支写成已执行操作。

反例：“进入本轮对话或所列受控初态，切换简历和模式，取消后核对焦点。”它缺入口、对象、按键和观察方式。合格记录应能回答：哪个对话、从哪个控件打开哪种窗口、选了哪份简历、按什么键到哪个控件、用什么方式取消、关闭后焦点如何测得。答案由本轮记录提供，不凭经验补齐。

历史报告只按已有操作记录、截图、输入及同轮前置用例还原。缺失的按钮名、按键、原文或对象标识就明确写“原始记录未保存……”，区分可还原操作与复现缺口；不把推测写成精确事实。通过平台审计更正接口保存，原始证据与状态保留。不因补写步骤自行重跑业务、发送消息或提交缺陷。
