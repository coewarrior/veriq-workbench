# 高效执行与等价取证
## 当前平台全局范围（2026-10-26）

当前平台全局范围：多账号、双账号、跨账号及跨租户对照/隔离业务场景一律不测（用户明确排除多账号场景）。保留具体设计和已有真实结果；未执行项使用 not_run，not_run_reason 填写上述原因；UI cases.account_scope、API design.account_scope 使用 multi_account/cross_account/cross_tenant 明确范围。不算通过，不申请第二账号、不等待账号集合、不为其创建执行会话或续接，不另做替代测试。普通继续测试/重测不解除此规则。不同模块各用一个账号并发仍允许；单账号权限、匿名及其他适用风险覆盖保持。已有真实对象责任的必要清理和无需账号的报告仍按原授权及回收协议处理，不扩展业务测试。

此明确范围变更优先于下文历史多账号示例；既有隔离、授权、清理及回收协议仍保护历史现场，不授权发起新多账号业务。


资源等待遵循 [共同前置与原节点阶段安排](work-stages.md)：先做当前合法可做的原场景，资源边界用完整阶段令牌，真实退出后明确 yield；原用例、覆盖、顺位与未知写入保护保持。

**默认路径：** [原生 Codex 执行](native-codex.md)。新任务直接使用持久 node_repl/Playwright 独立 Context，旧在途沿原工具，平台调用止于账号分配、结果/证据同步和 S1 停止。下文标为旧 Runner 的接口只供原任务兼容，不得混入原生步骤。

本文件用于实际执行 UI 测试。目标是在不改变设计覆盖、每条用例判定条件、证据真实性和环境收尾的前提下减少重复操作与等待；不是精简用例的规则。

用户要求比较模型强度或执行策略时，另读 [质量与耗时对照实验](experiments.md)。普通功能测试无需建立实验分组；实验也不改变原有探索、增量设计、逐条判断与授权范围。

模块分工、资料核对和事件纠偏统一见 [协调职责](coordinator.md)；账号与环境绑定见 [原生执行](native-codex.md#账号与实际登录环境)。不把这些准备重复插入每条用例。

## 已有结果与已跑通链路优先复用

同轮、同对象、同条件下，确定回执及其返回现场已能满足当前断言就直接前进，不再额外截图、查表、刷新或重读同一结果。已经确认的定位器、登录态、原对象、准备数据和工具格式直接复用；条件或结构实际改变才重新处理。一次现场可支持多个检查点时关联同一证据，不重演步骤。用户明确要求、原用例本身的重复性/持久化断言、结果未知或证据矛盾才需要相应补核；不能用“严谨”作为自动重复的理由。真实业务异步等待使用工具内条件等待，不由模型逐次轮询。

准备沿用当前已核验客户端、工具公开文档和原设计；已明确的参数不重复查清单，正常测试不查询平台源码、扫描内部实现或逐条编写临时上传/保存脚本。真实接口失败只查对应说明和错误字段，保留已完成业务的原观察。需要平台排查时将其与业务验证分开计时；平台故障不能改记业务失败，也不能靠重演业务解决保存格式问题。

收尾对已有记录做差额核对，只处理具体未满足项，不重新执行全部步骤来验收报告。已确认失败或共同前置阻塞一次即记录并停止同条件重试；只有条件实际变化才继续。保留未验证事实及影响范围，不将停止重复检查写成通过。

## 定向回归与有界收尾

本节适用于用户明确选中的历史用例回归，包括只测一条；不把模块完整测试改成抽样。用户明确约定的时间和现场保留要求优先。

- 开始时核对所选 ID、原设计、本轮初态和授权即可；复用已读取且未变化的需求、工具格式与环境结论。平台已准备本轮基线时直接使用；尚未准备时按原设计建立一次未执行基线，不重写设计或重建整个需求矩阵。每条仍实际执行原设计的必要断言。
- 测试写入前记录需恢复的原值和对象归属。原值被脱敏或不可读时优先使用本轮合成对象；不能猜原值，也不能承诺可恢复。无隔离替代时如实记录恢复限制，不能在收尾时搜索或猜测用户数据。
- 最后一条用例判定及其必要证据完成后，明确进入收尾；同时保存尚未回写的结果。进度区分“业务验证完成”和“正在收尾”，写清剩余对象，不提前声称已全部交付。只处理具体未满足的断言或证据缺口，不因通用覆盖建议重开已完成用例；无关新发现留作后续事项。
- 定向回归的数据清理默认使用一次 120 秒窗口，在首次清理操作前创建 `createCleanupGuard({timeoutMs:120000})`，同一轮各批次复用它。已知大批量清理或服务等待确需更长时，在开始前依据对象数和服务时限明确预算与原因；不得因失败而反复续期或重建守卫。工具不能导入模块时用同一截止时间实现等价检查。该窗口只限制新增数据清理操作，不截断业务测试、不强杀在途写入，也不跳过浏览器资源关闭及报告保存。
- 每个清理回调接收 `{remainingMs}`，将工具调用自身超时限制在剩余窗口内，并核对实际状态。清理调用结果不确定就停止该组，不能重发。同条件失败有确定证据后即停止该组；不得循环点击其他同类对象绕过停止规则。明确的独立恢复入口可在剩余窗口内尝试；不要为清理再创建 AI 对话、生成新简历版本或展开故障排查链，除非这些正是预先约定的恢复方式。
- 到期后不再发起数据写入。依据已有对象清单逐项记录未清理/未核实及原因，`scene_outcome` 如实为 partial/unverified；没有操作的对象不能写成“删除失败”。完成独立的浏览器资源收尾后立即交付。已知原值可以恢复的配置优先于批量删除安排，避免把可恢复配置留到预算末尾。
- 原生模块先真实关闭本任务页面，再按原生参考将最终元数据和报告放入同一次 finish/交接编排，直接使用 publication 回执；旧 finalize-ui 入口保留。发布只使用待保存的变化字段、既有截图关联及一份简短总结。用 `finalize-ui` 或现有 MCP 保存并发布同轮，成功回执已含原轮次和报告链接即可结束；仅回执缺失或矛盾时补一次只读核对；不重读全量用例、重算相同统计、逐条改写未变化文案或重传同一截图。真实保存错误只修具体字段，结果不确定先只读核对，不重新执行测试。清理残留不阻止发布，用户无需等“全部清干净”。

120 秒是定向回归新增数据清理的默认预算，不是总任务耗时承诺。守卫只阻止其管理的后续操作，不能终止已发出的调用或控制未接入守卫的外部工具；执行端必须同时遵守上述调用与交付规则。

## 执行批次与剩余范围

完整 PRD 验收和探索测试的覆盖要求保持不变。先在已保存设计中识别登录/角色、数据初态、上传、外部表单和结果观察等真实共用条件，用最小检查验证每组关键依赖并保存；尚未准备但能在授权内准备的条件应先准备。不能只确认页面能打开，就把全部后续用例视为可执行。某个前置受阻时及时给出受影响编号与剩余独立分支，缺少观察能力只限制对应检查点。

业务执行以共享页面、初态和恢复方式组成批次：控件与断言已明确后，将填写、提交、本次业务的真实完成等待、局部独立读回、逐项判定和必要恢复放在一次工具调用内，每条判定后立即保存成功再继续。一次页面状态能证明多个断言时复用原始观察与关联截图；需要不同输入、初态或隔离的断言仍独立执行。未知分支、实际差异和工具异常才中断批次判断，不为每个点击、字段或保存提示重新读取整页，也不先依据即时采样猜终态再以额外调用修正。字段组能一起保存时集中填入并逐字段读回，不以一个保存成功提示代替所有字段的断言。

`execution-batch.cjs` / `.mjs` 支持在原 steps 末尾追加新发现，保留原 ID 顺序与执行游标；不能删除、重排或换掉已有 ID。仅剩余回调会执行。若新场景必须先建立不同状态，则单独组织批次并保留原批次记录，不能重置已完成游标来凑初态。异常写入仍先只读核对，不因换批次而重发。

每个业务批次只回写变化字段及尚未上传的证据，使用保存回执中的 `progress_message`、`scope_change` 和 `execution_plan.execution_summary`，无需再次读取全量用例或手工脚本重算统计。读取用例时这些计数覆盖整轮，不受分页影响：`status_counts` 保留各真实状态；`determined_cases` 仅为 passed/failed；`remaining_cases` 和 `remaining_groups` 包含未完成验证、阻塞及等待，不把它们冒充已完成。`unchecked_dependency_cases` 只计已声明且当前需要检查的依赖，零不证明没有遗漏依赖；`runnable_cases` 只是调度候选，不是实际环境就绪证据。

上述“批次”是操作安排，不是积压整组结果后统一提交。默认原生路线的工具边界和逐条同步方式见 [连续执行与逐条同步](native-codex.md#连续执行与逐条同步)：受限 `cua` 只执行公开浏览器 API；外层清单未提供原生工具时不编造工具方法、不在原生会话中另造网络、文件或浏览器控制通道。已知动作、真实完成等待和局部断言连续执行，未知分支和异常仍返回判断；未提供同调用保存或外层原生编排能力时，在用例完成边界调用标准记录入口；不能退回每个动作返回模型，也不能通过省略真实完成等待和断言维持连续执行。

设计扩展使用同一任务 execution_id 下的稳定 case_id 追加或更新。新发现写明来源、必要断言和与已有用例的差异；已有用例已覆盖的断言直接关联证据，不再次复制设计、重测或另开完整轮次。追加后用 `scope_change` 明确“此前多少、本批新增多少、当前多少”；新增范围必须有新的风险或证据缺口，不能为满足泛化检查建议不断扩充同一问题。PRD 本来要求但漏测的项目应标明是补齐遗漏，不能称作额外成果。

进度用本轮已判定、验证未完成、未执行、阻塞/等待及剩余模块说明下一批；有新增范围或阻塞变化才补充说明。旧轮阶段报告另列其范围和结果，不把旧轮已花的时间除以新轮用例数，也不把阶段报告说成全部完成。所有本轮必要断言已有结论或已核实具体执行限制时进入收尾，不为了改文案重建下一轮；真实重要遗漏仍在当前范围内补齐。

遇到轮次或 revision 冲突，先持久保存本轮观察，按已绑定的 project_id/execution_id 只读核对一次。revision 变化仅重放尚未保存的字段更新；任务已发布时继续增量更新同一报告；执行已被明确的新任务替换时按 platform.md 的独立任务及审计更正流程保留已发生的事实。不得自动跟随别的聊天当前轮次、把它选中的用例并入自己范围，或为解决保存冲突重做已完成业务步骤。共用账号的操作和断言遵循 coordinate_ui_resources，工具恢复后先核对原对象，不重建提议或测试数据。

## JSON 文件与统一 CLI

有终端和已核验客户端时，直接用文件编辑能力将实际参数保存为本轮私有 UTF-8 JSON（权限 0600），优先调用现有 CLI。避免只为拼接参数、读取同一份 JSON、上传文件或发布报告另写临时 Python 源码，尤其不要把中文 JSON 嵌入 `python -c` 或 stdin Python。实体夹具生成、浏览器操作和确需计算的逻辑仍可用必要脚本；只有 MCP 时沿用原工具，不为此更换环境。

默认原生任务逐条保存使用 [标准原生结果记录入口](native-codex.md#标准原生结果记录入口) `native-record`：复用一次准备的绑定文件和当前已核验清单，保存成功后自动沿用最新 revision，回执及真实保存耗时落盘。浏览器仍直接调用本轮已绑定原生工具；客户端不代理动作，不把“准备记录工具”变成新增服务或反复编写临时脚本。下列通用 `call`、上传和最终收尾入口继续保留。

以下文件名是本轮工作记录的示例，不要求固定文件数量。变量来自当前已保存的会话、轮次和最近成功保存回执，不猜测、不自增 revision；命令按实际阶段分别使用，不整段盲跑：

```sh
# changes.json：project_id、execution_id、revision、cases 及本批真实变化字段。
python3 "$CLIENT_PATH" --url "$WORKSPACE_URL" call save_ui_test_cases --args-file changes.json --output-file save-receipt.json
# assets.json：沿用现有上传清单格式，file、case_id、step 及需要的 kind/captured_at 等。
python3 "$CLIENT_PATH" --url "$WORKSPACE_URL" upload-files --project "$PROJECT_ID" --execution "$EXECUTION_ID" --manifest assets.json
# finalization.json：实际 summary，以及尚未保存的 cases/coverage/review_notes/scene_outcome；实验任务可附 experiment。不要再带项目或轮次字段。
python3 "$CLIENT_PATH" --url "$WORKSPACE_URL" finalize-ui --project "$PROJECT_ID" --execution "$EXECUTION_ID" --revision "$REVISION" --input-file finalization.json --receipt-file finalization-receipt.json
```

上传清单按现有约定使用 UTF-8；`call` 和 `finalize-ui` 的 JSON 读取也兼容 UTF-8 BOM。检查退出状态与回执中的当前 execution_id/revision/phase，成功后再确认本地变化已回写。`upload-files` 在本次进程中复用文件读取/编码，跨 CLI 进程不共享缓存；已上传且未变化的附件复用真实关联，不为缓存额外上传或重跑命令。参数格式以当前 `agent-tools.json` 和客户端帮助为准，校验失败只修实际字段，不能改写测试结论迎合校验。

已知所需工具时，可用 `python3 "$CLIENT_PATH" --url "$WORKSPACE_URL" tools --name save_ui_test_cases` 精确查阅：完整保留所选工具对象（含参数定义）、对应 action、全部全局说明及其他顶层字段；省略 `--name` 的全文输出不变。此选项只减少终端展示，仍读取完整清单，不增加参数校验、自动修正或质量判定。未在 schema 展开的业务条件仍按原 Skill 与实际返回核对；不能据此跳过覆盖、证据或收尾要求。

`finalize-ui` 可选加 `--summary`，集中显示报告入口、轮次和返回信息；完整结果仍原样保存在同一份 0600 回执，默认终端输出不变。同名字段且 JSON 内容完全相同的返回信息只展示一次，并通过 `sources` 注明原位置；不同提醒和未知字段仍保留。它只减少重复展示，不判断质量、覆盖或清理是否完成，不能据此跳过审查。原输入与回执已经完成时，再运行同一命令并加此选项会复用现有回执，不发送新请求；不为查看摘要删除回执或重发不确定操作。`call --output-file` 的仅输出保存路径行为继续不变。

最终收尾复用已有逐条结果、依赖检查、证据和资源清单：先完成原约定的语义遗漏回查、必要补测与资源核实，将尚未保存的实质变化归入同一份最终 JSON，再调用 `finalize-ui`。它按需保存一次后发布同轮报告；若最终变化已成功保存，只传 title/summary，不再重复带上 cases、coverage、review_notes 或 scene_outcome。每批 200 条仍只是传输限制，超出时按原约定先分批保存，不能截断。阶段切换、异常中断、人工付款暂停等原有及时持久化要求继续执行，不能把全轮结果积压到最后。

最后一条业务结果已确定时即保存业务结束时间；后续证据传输、数据恢复、浏览器退出、报告整合/发布和资源交接分别记录。已有真实结果足以形成报告时复用平台总结能力，不再次编写统计脚本、重新下载用例或逐条润色未变化文本。报告需要补充的具体业务解释仍保留，不能为压缩时间省略失败影响、未验证范围或现场残留；报告整合耗时如实列出，不全部归作浏览器执行。

发布后复用保存回执与已有证据，仅有具体缺口时读取对应报告或关联数据；没有新的事实时复用已核实的结果，不为文案、计数或已经确认的清理重跑保存与发布。验收若新开预览标签，关闭并核实该标签；不要为此重建整套业务收尾或重复发布。发现真实遗漏、证据错误或资源残留仍继续处理并如实记录，沿用同一任务报告并保留历史证据。回执非 published、请求结果不确定或 revision 冲突时，沿用下文只读核对与恢复约定，不删除回执或直接重跑整段命令。本节仅组织已有工具调用，不新增发布门槛、硬时限或覆盖上限。

## 一次预检，立即分流

按 SKILL.md 的用例执行范围规则，预检发现数据或状态尚未准备时，先在现有授权内准备并核验；不要直接登记 blocked。缺少当前页面入口时检查该用例相关的导航与关联入口，真实不可达才记录缺口。收尾计划为 report 时先回查是否误把可准备条件、部分未完步骤或可执行用例标为阻塞/人工，再决定交付。

预检先判断业务链路能否到达：从本轮目标识别真实主入口、所需角色登录、关键业务状态（例如可处理订单或已建立的任务）、结果观察通道。页面侦察阶段集中核对实际可见入口和安全可用的替代入口，避免先把对话入口的差异当成整个功能不可用，直到收尾才发现批量入口。账号、登录、状态和观察能力不齐时立即建立共同条件；权限最大不等于这些条件已经具备。侦察不冒充正式用例通过，仍在正式逐条执行前保存完整具体设计。

保存和检查返回的 `execution_plan.next_action` 是本轮诊断建议，由 Codex 结合真实条件和原范围决定下一步；它不修改保存结果，也不据此阻断资源候选：

- `check_dependencies`：参考 `dependencies_to_check` 的影响范围选择必要检查，共用条件一次记录；根据新事实调整，不照旧清单继续探测已经确认无意义的下游条件。
- `execute`：参考 `runnable_case_ids` / `runnable_checkpoints`，由 Codex 按实际前置、断言与资源归属决定推进哪些用例。`blocked_dependency_groups` 给出共同观察和受影响编号；`deferred_dependencies` 暂无必要检查，条件变化后再评估。人工执行的设计保留，不能冒充 AI 可执行。
- `report`：当前诊断计划未列出可推进项，不证明业务范围已经无工作可做。复用已有逐条结果、证据和资源清单，由 Codex 完成必要的语义回查与现场核实后及时发布；不持续等待、不继续换会话重试，不为诊断建议批量改写原结果。它不代表完整验收通过，未验证范围仍须明确披露。回查发现独立且可执行的重要遗漏时先补充并执行，再按新事实收尾。
- `design` / `review_report`：分别表示尚无设计和本轮已经发布；前者先预检并保存设计，后者复用现有报告，不能因读取计划又发布一遍。

第一次确认关键阻塞时，就向用户说明共同原因、受影响范围和剩余可执行分支，不等最终报告才暴露大部分无法执行。耗时应分清有效业务验证、阻塞检查及保存收尾，不把阻塞条数当执行成果。没有新状态、新证据或新的独立风险时停止扩展相同路径；条件变化或新发现确实能改变可执行范围时才恢复。禁止按固定阻塞比例或硬时限丢掉仍可执行的重要场景。

同一业务用例包含可操作页面与缺失的埋点/账本观察时，用 checkpoints 把条件挂到对应观察步骤，不能把整个用例挂在缺失观察能力上。登录拒绝等逆向场景不依赖成功登录。服务端仅按明确关联归组，不根据相似文案猜测，更不会把前置就绪等同业务通过。

执行开始时只做一次轻量预检，并在本轮复用结果：可用浏览器控制、固定目标标签/页面句柄、登录会话、文件选择能力、可设置视口、现有角色/租户、屏幕阅读器或真机能力。按 [浏览器控制约定](browser-control.md) 绑定目标后再操作。已有能力立即使用；缺失能力按 platform.md 的 bootstrap 约定只补一次。仍缺失时把对应完整用例直接标为人工或 blocked，写清缺少条件，继续其他场景；不要对每条同类用例重复探测、安装、登录或等待。

预检结果是内部执行状态，不新增用户步骤，不作为报告卡片。后续真实状态变化可修正预检结论。同轮或解锁续测复用已核验的 Skill 摘要、客户端、页面句柄、用例和夹具；只检查变化的登录/控制状态。不要重新下载、全文打印、重建全部基线或重做环境检查。平台要求新轮次时保留必要设计，但只为新增或变化项组织新的内容。

## 用依赖图组织，不按编号逐条重置

保存完整设计基线后，根据共享初态、状态变更和清理关系形成执行批次：

- 同一页面和登录态下的只读断言集中执行，避免重复导航和登录。
- 在同一浏览器上下文中复用已经核验的登录态、页面对象和稳定前置状态；每条用例仍单独执行必要动作与断言、单独记录结果。需要新会话、权限隔离、缓存隔离或污染检查时必须新建上下文，不能强行复用。
- 一次创建的合成对象可依次验证默认状态、查询、修改、停用、恢复和删除；每条用例仍独立记录输入、断言、结果与证据。
- 会改变同一对象或依赖先后状态的用例保持串行；相互独立的页面、问答、文件或账号数据可安全并发。
- 安全并发默认从少量工作单元开始，并以工具和目标系统可承受为准；出现限流、状态串扰或资源争用立即收敛，不把并发故障判成产品缺陷。
- 多个测试任务复用同一浏览器时，各自绑定专用标签/页面句柄，并核对共享登录态和业务数据是否冲突。共用同一标签或依赖前台的原生文件选择框时，操作不是独立资源：确认本任务持有该资源后再操作，其他任务使用时等待或切换到真正隔离的执行通道，不靠反复抢切前台标签解决。等待资源不记作产品阻塞；任务结束只释放自己创建或持有的资源。
- 多个用例共用观察时，只能复用能同时证明各自断言的真实状态；不能用一次粗略浏览给多条用例填通过。

先运行低成本、能建立后续状态的用例，再运行长耗时生成和破坏性收尾。失败会影响下游时，只阻塞真实依赖项，不连带停止独立分支。

遇到不可执行项，先保存已有输入、动作、观察、具体缺少条件及受影响的用例或检查点，再从原设计和探索笔记选取下一项不依赖它的工作继续执行。跳过是本轮执行安排，不新增结果状态：沿用真实的 blocked、pending_action、partial 或 not_run 等状态及原因，保留完整设计、证据和对象清单，不改成通过，不删除范围。已知条件未变时不重复询问、等待或检查同一阻塞；条件实际变化后再恢复对应路径。只有剩余有价值的工作都依赖同一不可用条件时，才将整个任务描述为受阻。发布阶段报告不终止其他独立场景，清理残留也不阻止无关场景继续；继续执行仍遵守授权与资源隔离，不绕过工具限制。

共同前置条件按 platform.md 的 `cases.dependencies` 保存，不按错误文案猜测分组。执行前轻量检查一次并用 `record_ui_dependency_check` 保存结果；`execution_plan.skipped_cases` 仅提示可能受影响的步骤，由 Codex 结合实际条件决定是否继续，并显式记录各用例结果。阻塞状态仍可直接从本轮记录核实时，不逐条刷新、重登、上传或等待；数据和状态发生变化后再检查。可缓存同一 dependency.id 的真实检查，不以固定 blocked 分支阻止业务执行或资源候选；新轮次不继承旧检查。ready 只表示已记录条件恢复，不能代替各用例的业务断言。

## 稳定操作链在一次工具调用中执行

补测先读取 `get_test_document.retest_task` 和 `get_ui_test_cases`：平台已准备只含所选编号、结果重置为未执行的新基线。直接复用返回的 execution_id/revision，不从报告或文档重新手写设计。已有用例用 `save_ui_test_cases` 提交 `{case_id,status,actual,...变化字段}` 即可；未提供的设计和检查点字段保留，明确传空值才清空。新增或需要修正的设计仍按原约定完整保存。

整体回归入口 `start_regression_test` 也直接准备原用例基线。指定范围用 `case_ids`，未指定则复用完整基线；返回 `prepared_execution.execution_id/revision/cases` 和缺陷处理依据，原前置条件、输入、步骤、预期保持原样，历史结果与检查点证据重置为未执行。不要再读历史后手写整份基线。原前置要求新对话时必须用新对话，不能为了复用已完成对话而改变场景。当前 Codex 执行时传稳定 `request_id`、`holder_id`，客户端自动接上原任务队列、claim 和 context；未取得账号时保存原领取回执并结束回合，不重新创建任务、不循环领取；收到真实资源变化后才续接。资料缺失或用户明确改范围时才读取相应补充；准备完成直接测试。

主要成本可能来自工具调用之间的模型判断，而非页面本身。工具允许循环、函数或脚本时，把已明确的“输入→提交→等待完成→读取答案→展开引用→核对原文→记录结果”放在同一次调用，多个独立对象可在同一调用内逐个执行并分别保存结果；不要每点一次都回到模型重读整页。未知控件、改变流程的差异、权限变化和需要判断的新分支才返回模型决策。每个关键操作仍检查自己的断言，遇到差异先截图和记录，不能盲目继续整批。

**旧 Runner 兼容路线：** 平台受控浏览器在 `context.execution_host.browser_batch=true` 时支持 `browser_action=batch`：`parameters.steps=[{id,action,parameters},...]`，把已经确认的顺序操作连续执行。沿用已有业务授权，不逐步询问用户。每步保留稳定操作 ID 和真实回执；`check` 用 `selector` 与 `expect`（visible/enabled/text/value/count）判定，必要时先 `wait` 到目标状态。异常、未知结果或断言失败停止后续步骤，返回已完成与未执行步骤；据实际回执记录各自用例，不把一次批次成功等同所有用例通过。未知步骤不得重放。批次中间交互默认只返回摘要，最后动作默认完整观察；`response=full` 可保留中间所需页面，`snapshot_selector` 可限定观察区域。独立判定、截图和全部覆盖要求不变。

**旧 Runner 兼容路线：** 新版客户端在 `context.execution_client.browser_batch=true` 时自动兼容原执行机：同一个 `browser_action=batch` 在客户端内部顺序提交已有普通动作，保留每步完整回执，不重启浏览器。返回 `batch_transport=compatible` 表示减少模型往返，仍有原逐步网络调用；不是执行机原生批次。回执目录与原客户端凭据一起保留，超时沿 `client_wait.resume_arguments` 续接；未知提交只查询原请求，不自动重发。旧机不支持 `check/snapshot_selector`，仍须保留原实际观察和每条用例断言，不能为合批省略判断；需要分支判断时在观察处结束批次。原生批次、摘要和局部快照仍按执行机声明使用。领到就绪账号和浏览器后直接测试，普通独占任务不增加例行阶段交接、重复授权或每步重新获取 context。仍按已知动作和真实页面变化决定后续步骤，不能把尚未观察的分支写成已执行。

以下为已有脚本执行环境的可选复用方式，不是默认原生路线的前置；已经能在 `cua` 连续操作时直接使用原生循环，不另下载/导入 helper，不因此切换浏览器或等待模块加载。支持模块导入且原任务已选用该 helper 时，复用随包 [execution-batch.cjs](../scripts/execution-batch.cjs) 的 `createExecutionBatch()`。首次确认控件及断言后，在持久会话一次定义同组 `[{case_id,run:async({remainingMs})=>真实结果}]`；回调只用浏览器工具公开的 API，给操作设置自己的超时。`run(steps,{budgetMs,checkpoint,persistCase})` 连续执行到调用预算或首个非通过结果，返回编号/状态摘要。`checkpoint` 写任务私有本地文件；`persistCase` 在每条用例判定后立即调用原 `save_ui_test_cases` 增量保存，复用回执中的最新 revision，成功后才返回，失败必须抛错。工具成功保存后清除该条待写结果；保存失败保留结果和已完成游标，后续只核对并补保存，不重跑浏览器。旧调用方未传 persistCase 时，仍须每条完成后立即保存 `updates()` 中变化字段，平台成功后才 `acknowledge(ids)`。下一次调用复用同一对象和 steps，直接从断点继续；进程中断时用本地 snapshot 作为 `initialState` 恢复。异常操作可能已经生效，先只读核验并 `resolveInterruption(真实结果)`，不得直接重发。非通过结果核对后用 `continueAfterReview(具体原因)` 继续未执行部分。时间记录区分批次内执行与批次间间隔，不能把间隔直接当成服务响应慢。

检查点写入也计入本批预算；写入后预算已耗尽时保留当前步骤，下一批再执行，不启动零剩余时间的新操作。已经发送的操作仍等待其自身结果，不因批次预算耗尽而取消或重发。恢复快照的执行耗时包含生成该快照时已观察到的本批时间；不包含其后尚未完成的写盘或进程停机时间，不能据此宣称覆盖了中断期间的完整耗时。

仅支持 ES module 的持久会话使用同包 [execution-batch.mjs](../scripts/execution-batch.mjs) 的命名导出 `createExecutionBatch`；支持 CommonJS 的环境继续使用 `.cjs`。两个文件的执行实现相同，仅导出语法不同，不需要浏览器注入或替换浏览器控制通道。导入失败发生在操作前时记录该执行条件；原生工具能够直接完成时立即沿原页面继续，不为 helper 故障阻塞业务，也不将导入失败记作业务页面故障。

- 持久会话保存页面、稳定定位器、结果队列和资源清单；页面变化导致句柄失效时再重新定位，不反复读取所有窗口和标签。
- 标签关闭并重建后，复用的步骤和观察函数也需绑定当前明确目标；可将本轮页面句柄显式传入函数，避免闭包仍引用已关闭标签。不能仅凭外层变量已更新就推断既有函数已改绑。操作已发生而观察函数失败时，先只读核对当前页面并补完未完成核验，不重新执行已发生的操作；保留具体异常和已观察原值。
- 控件定位优先读取目标区域、可访问名称或状态变化；全页快照用于首次侦察和真实结构变化，不在每步、每条用例后全文返回。
- 单次工具调用有执行时限时拆成能在该时限内完成的小批次，并先落盘；不要用超大调用导致结果丢失。
- 每批只返回用例 ID、实测结论、关键值、耗时和新增异常；完整输入、原文和证据存在任务状态及平台，不在聊天中重复输出整份用例、清单和 Base64。
- UI 用例实际经过被测控件；已有授权且契约已知的 API 可用于准备数据、独立核验和清理，不把直接调接口冒充点击、文件选择或 UI 业务链路通过。

## 按测试类型选择批次边界与核验方式

以下组织方式用于已经侦察并保存设计的场景，不替代范围内的完整设计、逐条判定或执行中新发现的增量补充。按实际依赖选择，不要求所有任务采用相同批次大小，也不新增执行或发布门槛。

| 测试类型 | 可连续执行的部分 | 需要保留的核验与恢复依据 |
| --- | --- | --- |
| 稳定页面、只读查询 | 已确认控件及输入下，连续操作并分别读取每条结果 | 当前查询对应的数据与状态；各用例仍独立判断，不能复用旧列表作为新结果 |
| 条件表单、多步向导 | 在已知分支内输入、选择、前进和返回；按阶段组织批次 | 每一步核对实际分支和已知必填条件。逆向用例出现预期校验提示即按该用例判断，不因未进入下一步判失败；出现未知分支先保留现场并修正或补充设计，再决定后续动作 |
| 日期边界与派生字段 | 已确认年月切换、选择和退出方式后，同组输入与字段读回可连续执行 | 依据实际日期及适用时区独立计算已保存预期，不从页面派生值反推预期。日历可能显示相邻月补位，按完整年月日区分，不能只查日数字；选择、清除、取消或退出后分别核对输入、关联字段及保存状态，不把日历关闭等同整条通过 |
| 保存、修改等持久化流程 | 同一对象的有序操作，共享已核实初态 | 写入前记录对象归属、原值及本轮值，保存后核对已提交状态和独立读回；中断恢复先检查同一对象，从尚未完成部分继续，不重放整批写入。清理只恢复归属明确且仍符合本轮状态的对象，变化冲突按现有收尾规则记录 |
| 异步生成、多轮对话 | 明确输入与对应结果后的有序提交、等待、内容检查 | 记录当前会话、任务或输入的关联依据，分别核对受理、处理中、完成、失败或已取消的实际事实；这些事实不新增平台状态。处理结束后仍检查答案内容、最新更正及任务要求；主动取消用例按取消目标判定 |
| 键盘交互 | 从已知焦点出发，按实际导航键移动并逐步核对焦点，再激活目标控件 | 定位器可能自动聚焦，直接对目标调用按键不能证明 Tab 路径可达。取消、保存等按实际最终状态独立判断；发生差异时保留焦点、按键和读回证据，可用同对象鼠标操作作对照，不能用鼠标成功代替键盘通过 |
| 窄视口与响应式布局 | 在工具明确支持的视口下检查已知关键入口、滚动、弹层及恢复 | 记录设置前与实际生效尺寸，核对控件是否真正可操作。视口设置和恢复可能异步生效，不能只凭设置调用返回判断完成；恢复后核对实际尺寸。桌面窄视口不代表真机、触摸或移动浏览器兼容性 |

跨标签是同账号不同页面的核验方式，不能冒充跨账号或租户隔离；当前跨账号/租户对照隔离场景不测；其他需要隔离的操作仍使用实际可验证的角色与上下文。并发仍遵守前述独立资源约定，共享对象及前后依赖保持串行。

页面中断或工具超时不等于业务动作未发生。复用已记录的目标先只读核对一次，区别实际业务差异、预期的逆向提示和控制/定位失败；无法核实时沿用现有不确定结果与停止边界，不重复提交来“确认”。计时分别记录实际操作、工具间隔、等待及保存发布，不能把减少工具往返带来的收益称为服务响应变快。

## 等待真实完成条件

优先等待可观察事件，而不是固定 sleep：目标元素出现或状态变化、请求完成、按钮恢复、上传进入就绪/失败、流式回答停止增长、导航 URL 或标题改变。保留合理超时；超时本身是实际结果，不能无限轮询。

异步列表切换时，需核对本次操作关联的目标对象、结果列表或完成信号；页签已选中（例如 `pressed=true`）、加载图标消失时，旧列表仍可能短暂保留，不能据此认定结果已更新或直接判定失败。取消收藏后，先确认目标已从收藏结果中消失，再核对详情中的收藏状态；沿用事件等待与现有超时规则，不增加固定等待时长。

等待同时识别实际中间步骤和失败状态；新确认表单已出现时先按该状态继续，不盲等旧最终目标。加载文案从未出现或定位未匹配时，“已隐藏”不能证明任务完成，仍须核对本次操作对应的目标状态。同次可取得的局部计数、状态标签和必要证据合并观察；结论整理不再重复读取已经确认的状态。

同一异步任务只由一个等待者跟踪。返回不确定时先读取页面或平台状态确认，不重复触发提交、上传、生成、删除或发布。轮询采用递增间隔，并在状态变化时立即继续。

输入框可编辑、发送控件恢复、页面重新打开或其他任务区域显示空闲，都可能与当前任务仍在处理同时发生，不能单独作为完成依据。依据实际页面核对本次任务的状态与对应输出；重开同一会话后继续读取原任务，不重新发送。只有确实观察到处理中再执行关闭、取消等动作，才能声称覆盖了相应中断分支；先自然完成则如实保留该分支未覆盖。

AI 回复可能呈现为段落、列表、表格或可访问的组件内容。按当前回复的可见结构读取并核对事实、数量与约束，外层文本为空不代表没有答案；不能只查一种节点，或在整页搜索到输入提示、历史答案中的预期词就判本轮通过。沿用浏览器公开能力，不读取应用隐藏状态来替代用户可见结果。

文件预览也可能以页面图像呈现，DOM 文字未命中不能单独证明解析失败。核对当前文件的实际预览与合成原文关键事实，保存可检查的视觉证据；上传受理、解析完成、内容正确和刷新后仍可读取分别依据实际观察判定，不能只因列表显示已上传就声称整条文件链路通过。

可访问角色不等于 DOM 元素类型，例如 `img` 角色也可能由 Canvas 提供；使用完成状态或尺寸属性前先核对实际元素及工具可观察能力，不能将 HTML 图片专属属性套用于 Canvas。状态就绪条件应覆盖本次要读取的结果集合，单个条目可见不代表整组数据已就绪。组合检查中断时保留各项实际观测值和对应现场，不仅记录一个异常名称；后续只读核对若恢复正常，明确最初缺失的证据，不倒推或编造首次失败原因。

优先用浏览器 API 自带的事件等待与超时；否则把只读轮询放在同一次有截止时间的工具调用内，只返回完成、超时或控制阻塞。截止时间到达后保存最后状态，不再开启一轮相同等待。没有产品 SLA 时，等待超时只能证明尚未观察到完成，不能自行判成性能缺陷。工具支持模块导入时可复用 [execution-guard.cjs](../scripts/execution-guard.cjs) 的 `waitForState(read,{timeoutMs,intervalMs})`：read 返回 `{done,blocked,...}`，blocked 只表示设备/控制等已证实阻塞；读取 API 支持超时参数时使用回调传入的 remainingMs。该 helper 不会终止已经发出的操作，不用它包裹重复写入。

点击或按键调用返回不等于对应状态变化已完成。例如 Esc 关闭弹窗时先等该弹窗实际隐藏，再核对草稿、焦点和页面；导航后先确认目标页面及要操作的控件已到达，再执行刷新或下一步。一次即时可见性读取只代表采样时刻，不据此判最终失败。若此前采样与后续状态不同，保留两次事实和时间关系，从已知初态复核，不把测量过程中的中断冒充产品缺陷。

确认弹窗触发导航时，下一页标题可见也可能与上一确认仍未完成关闭同时发生。连续操作前分别核对原确认已关闭、目标页面已到达，再执行下一次导航；只使用当前工具可观察的实际状态，不增加固定延时。改进后的重复成功不能倒推先前中断的根因；按实际保留先前未完成的步骤、补充就绪条件及后续各轮结果。

## 已知失败及时停止对应路径

- 锁屏、控制断开或资源冲突已明确时，只尝试一次有依据的恢复；工具已报告自动恢复失败就计作这一次。不能恢复立即停止受影响的 UI 分支，保存结果与资源清单并交付阶段报告。无需等待用户回应后才结束当前阶段，不继续十几分钟补设计、重复扫描设备或改写全量用例。解锁等用户可解决事项用 pending_action/manual_step，其余客观依赖用 blocked；剩余完整设计保留。
- 同一操作、接口/入口、对象类型、角色/租户和前置状态下，同一失败已有明确初态和对应结果证据即可记录该路径当前不可用，不默认再次独立复现。先保存证据，不为同一失败继续换对象、刷新、重登或重新发请求；不同业务条件、格式、权限或独立入口仍按各自断言验证，不能把同一个错误码当作整站不可用。
- 清理复用测试中已确认的失败：删除用例已经确认失败且条件未变，进入收尾时不再对同类对象重试。首次在清理中遇到确定失败即停止该组；结果未知时只核实原操作，不重发，继续独立类型的数据清理、配置恢复和浏览器关闭。
- 提交后持续加载或响应不确定时只读核对一次。仍无法核实时停止该组写入，不对下一个同类对象发删除。条件恢复、有新的有效通道或用户明确要求复测时，记录变化后才重开已停止的路径。
- 停止清理的对象按已记录的归属清单和可用的批量查询列出残留，统一记录原因，scene_outcome 为 partial/unverified，items 中仍逐项保留名称与状态；不用逐个再次点击、逐个截相同错误或将未尝试对象冒充删除失败用例。保留证据、报告与重建数据，不能把停止写成已清理。

有 JS 模块能力的执行环境可在任务持久会话导入同包 `execution-guard.cjs`；只有受限工具时，在其允许的循环里实现相同停止条件，不为导入 helper 更换浏览器或安装依赖。`createCleanupGuard()` 的 failure(group,failureKey,reason) 可导入此前已核实的失败，group 明确包含操作入口、对象类型与角色/租户条件；不能只用“删除”合并所有类型。`cleanupBatch(ownedItems,attempt,guard)` 保留每个对象并汇总结果。attempt 必须操作归属已核实的对象并检查实际状态：删除已核实才返回 `{state:'cleaned',reason}`；核实失败返回 `{state:'unverified',confirmedFailure:true,failureKey,reason}`，一次已确认失败即停止同条件整组，不自动再次调用 attempt；持续加载或不确定返回 `{state:'unverified',reason}`，直接停止该组而不重发。回调抛异常也按不确定处理。锁屏后调用 guard.stopAll(reason)；重开单组必须 guard.reset(group,changedCondition)，同时重新核验状态。

## 测试数据与证据

在执行相应批次前一次性生成并核验所需合成数据；能复用的实体夹具不重复生成，但每个使用它的用例都明确引用。边界值、文件格式和安全输入保持独立判定，不能为了少操作合并成一个含糊结果。

- 通过场景保存足以证明断言的状态和文本，不重复拍摄相同页面。
- 失败场景保留对应截图和实际观察。同条件已有明确初态与结果证据时不默认复现第二次；仅证据不充分、条件变化或用户要求时补核实对应缺口，不为收尾再跑一遍。
- 录屏只用于难以用静态证据表达的瞬态问题。
- 无关的连续全程截图、重复导出和每步视频会增加时间且不提高结论可信度，应避免。

## 增量探索与保存

执行中发现新入口、规则或风险时仍要补充用例。只有带来新的功能、状态、规则分支、异常恢复或安全风险时才扩展；文案重复、同构控件和已经被同一等价类可靠覆盖的数据不机械重复。

结果持续写入本地工作记录，在每条用例完成独立判定后，立即将该条变化字段及检查点用 `save_ui_test_cases` 增量回写，不等待整组或整个模块结束，沿用 execution_id 和最新 revision；每批最多 200 条是传输限制，不是测试总量或必须凑满的批次。不每次点击、每个检查点或按固定秒数单独写平台，执行工具已经保存的结果不重复提交。该条用例的变化字段与检查点合并传输，不合并独立用例的判定、输入和证据。多个证据文件准备好后用 `upload_ui_test_assets` 或 `upload-batch.py` 一次传输；平台逐项执行与单文件完全相同的校验并整批写入，单个文件仍可沿用原工具。发布前统一读取本轮记录，核对用例总数、状态、测试数据、失败截图、清理结果和 `fixture_reference_mismatches`，最后只发布一次。阶段切换、请求人工补充、异常中断和退出前先保存待回写结果；人工付款暂停前立即持久化原订单关联，不能为凑批次延后。

`update_task_progress` 仅用于阶段变化或新的阻塞/异常，已有必要调用自动记录同一进展时不重复上报。同一阶段没有新的事实就继续测试，不按每分钟或每 6 秒发送心跳，不为更新概况计数额外回查。网页独立读取已有记录；概况随每条用例的结果保存更新，不把每次点击当作已完成用例。

原有前置、输入、步骤和预期不反复重写；只更新受影响用例的实测、结论和状态。续测不把上轮结果算为本轮通过。回查以新增风险和真实缺口为依据，不为美化文案反复读取整份报告、重算相同统计或上传同一附件。常规收尾先停止循环、核对资源、批量回写、一次发布；控制阻塞的阶段应立即交付，不能以无限补充或重复格式检查延长。平台结构校验若失败，只修具体项并复核一次，保留真实缺口，不声称已发布。

本地文件上传优先复用已核验客户端的文件入口，不另写逐项读取和 Base64 编码循环。可直接运行 `python api-test-client.py --url "$WORKSPACE_URL" upload-files --project "$PROJECT_ID" --execution "$EXECUTION_ID" --manifest assets.json`；清单格式与 `upload-batch.py` 相同，每项包含 `file`、`case_id`、`step`，可附 `kind`、`captured_at`、`filename`、`content_type`。自编 Python 脚本复用同一个 `Client`，调用 `client.upload_assets_from_files(project_id, execution_id, entries)`；需自行组织请求时用 `client.asset_from_file(file, case_id=case_id, step=step, kind=kind)` 构建每项。客户端仅在该实例内复用未变化文件的读取与编码，文件变化即重新读取，缓存有内存上限；每条用例的关联、步骤、时间和服务端校验仍独立保留。原始 Base64 工具参数与 MCP 调用仍可使用。

已核实实际结果、语义回查、证据关联和资源收尾后，可用客户端 `finalize-ui` 入口复用既有保存与发布工具，避免另写中文 stdin Python 脚本和反复读取、计数、补写同一轮。运行 `python3 api-test-client.py --url "$WORKSPACE_URL" finalize-ui --project "$PROJECT_ID" --execution "$EXECUTION_ID" --revision "$REVISION" --input-file finalization.json --receipt-file finalization-receipt.json`。`finalization.json` 是 UTF-8 JSON 对象：`summary` 为实际报告总结，`title` 可选；`cases` 只含本批真实变化项（最多 200 条），可附原约定的 `coverage`、`review_notes` 和 `scene_outcome`。同一编号的不同观察先核对再组织最终更新，不自动取最后一项；共同前置字段仍按 platform.md 填写。`scene_outcome` 必须来自实际对象清单，保留或未核实项不能声明整体已清理。此入口不会测试、清理对象、推导状态、补通过或判断覆盖完整性；结构提醒与实际语义缺口仍按原规则处理。

可选现场记录格式为 `scene_outcome={status:cleaned|retained|partial|unverified,note,items:[{case_id,name,kind,state:retained|cleaned|unverified,reason}]}`。逐条 `cleanup` 或报告 `summary` 不能替代该结构；必须根据本轮真实对象和核验结果填写，不自动从文字推断。缺失时仍显示“未记录收尾结果”，不默认算已清理，也不新增发布门槛；可通过同轮 `save_ui_test_cases` 的 `cases:[]` 单独保存。

入口一次调用 `finish_test_workflow`，把最后一批显式变化、总结和实际清理记录一起交给平台。平台保存一次；原生路线按 S1 及执行者/用户真实退出确认交还账号，旧 Runner 由原执行机确认浏览器退出后交还账号，生成最终报告并按已有设置推送；阻塞、部分验证与未执行照实保留。不需要先发阶段报告、结束后再补发。无变化时不重复保存。回执以 0600 权限保存；重复运行完成回执只返回原结果。原生返回 `native_closeout_required` 或 `manual_stop_required` 时，按实际会话/模块清单处理真实退出与交还，立即结束这次等待，不轮询 settling 状态代替退出。只有旧 Runner 的 settling 回执沿原只读查询等待，不重复保存或重新执行业务。响应不确定时读取原回执和平台状态核对原请求，不重放写入；真实修正用新 request_id 和最新 revision。旧 Runner 结束回执包含服务端浏览器命令计时（含等待和失败，不含模型思考/HTTP往返）；原生路线的工具耗时取自实际原生调用记录，平台未接管动作，不冒充有服务端浏览器命令计时。直接引用各自已有统计，不另写脚本遍历所有操作文件、不要为计时再改报告。客户端 JSON 文件/stdin 和输出均使用 UTF-8。

## 本地预检与集中验收

文件准备好后，用 `python3 api-test-client.py --url "$WORKSPACE_URL" check-files --manifest assets.json --cases-file cases.json` 一次检查清单。cases.json是本轮已保存的完整用例列表或含cases的读取结果，不能把单页当全量。只预检本地可读性、关联编号和fixture文件名引用，不读取完整文件、不编码、不请求平台、不代填设计。按返回的问题序号和类别修正源JSON后，upload-files带相同 `--cases-file` 在写入前复核；服务端仍做最终校验。没有本地用例快照时可省略此参数，不为预检反复读取未变化记录。

不为截图转换引入PIL等额外依赖：现有文件入口按原始字节识别格式，必要夹具生成复用已核实环境。finalize-ui成功回执已有保存revision、覆盖提醒和报告入口；发布后将必要的报告可读性、证据关联、清理核实集中一次完成并保存结果，只对明确缺口追加回查。不为同一报告另写多段Python或反复下载前端源码；不替代业务断言、语义回查、失败证据与资源清理。

## 等价性检查

优化后的执行只有满足以下条件才与逐条执行等价：

1. 设计范围和用例数量没有因速度被删减。
2. 每条已执行用例的前置条件真实成立，所有必要断言均有结果。
3. 共用状态没有让用例互相污染；需要隔离的用例使用独立对象、会话或账号。
4. blocked、partial、pending_rule、pending_action 和 not_run 按事实保留，不改写成 passed。可由用户在报告中决定或完成的事项用 pending_action，不得混入 blocked。
5. 失败复现、证据和清理标准没有降低。

任一条件不成立时，回退到较小批次或串行执行，而不是牺牲结论可信度。


### 原设计与结果复用；旧 Runner 回执兼容

严格遵守：已有设计只读一次并复用，不为报告重跑业务或重写整份设计。`start_regression_test.prepared_execution.result_template` 已提供本轮结果填写结构；CLI `call start_regression_test --output-file start.json` 会直接落下 `design.json`、`results.json`、`browser.json` 并返回路径。`browser.json` 可用于原 `direct_test_session --base-args-file`；排队仍按原回执续接，不另建任务。重复启动回执不会覆盖已填写结果。

结果仅提交 `case_id` 和发生变化的实际字段。已有检查点用 `checkpoint_updates=[{id,status,actual,verification_mode}]`，未更新检查点和原预期/依赖保持原样；验证方式仍由实际执行决定。不要为了格式复制整份 checkpoint，也不把工具成功当业务通过。

最终 `finish_test_workflow` 或 `finalize-ui` 可以省略 summary/title，由平台按真实结果、未完成检查点和 scene_outcome 生成总结。仅旧 Runner 已有直接浏览器回执使用 `evidence_refs=[{case_id,lease_id,request_id,step}]`：平台从本轮已保存回执生成 JSON 观察证据，和最后结果一起保存；无需下载再打包上传、改测试输入引用或再查询 revision。它不执行任何浏览器操作，不补造断言，不把截图字节当文本证据；确需的原截图仍沿原截图入口保存。

本地外部 JSON 观察证据使用 `kind=observation`，不再冒充 `fixture`。fixture 用于真实测试输入，通过 case_id、step 显式关联，由 Codex 核对用途，不要求文件名出现在用例文案中。清理仍按真实现场执行，不能自动标为成功；记录保留对象和失败原因后直接结束，不为补写总结再次查页面。


## 无账号的会话休眠

claim 返回 queued 且没有 lease_id 时，保存原节点、holder、dispatch 和续测位置，结束当前轮次并停止本地领取进程，不连续调用 claim 或 wait_threads。平台保留原顺位；协调者只在收到实际账号交还/资源变化且存在已核实的会话唤醒入口时恢复原会话，不定时唤醒模型检查。旧 Runner 可沿原单节点暂停入口处理；原生路线不为等待增加新协议。暂停与分配发生竞争时先核实退出，不能把未知占用当作空闲。已持有账号的正常测试不受影响。平台资源状态由协调者集中检查，不让每个等待会话各自空转。

原生 `finish` 返回的持久 `handoff` 沿 [账号交还后的持久交接](native-codex.md#账号交还后的持久交接) 完成一次真实消息通知和原 `dispatch` 消费。消息未知不自动重发；消费不是领取成功，仍按原节点、顺位和范围领取。仅生命周期边界处理，不增加逐动作查询，也不把平台保存事件或本地文件说成会话已经唤醒。


## 旧 Runner 已知用例连续执行兼容入口（0.17.36）

此入口只兼容原 Runner 任务；原生 `native_browser` 使用 [原生 Codex 执行](native-codex.md)，不提交 browser batch 或为此安装 helper。

当 `context.execution_host.case_execution=true`，已有确定动作、预期和原检查点的用例使用原 `browser_action=batch`，提交 `parameters={plan_id,cases:[{case_id,steps,checkpoints:{原检查点ID:[check步骤ID]}}]}`。执行机按顺序执行原生步骤，以真实 check 回执更新对应检查点，每条通过原 cases 接口保存后才执行下一条；不需要模型逐步发命令或另写结果回写循环。原输入、步骤、预期、未安排检查点和已保存证据保留。只按全部检查点的实际结果判定整条，不以点击成功判为通过。已完成用例不重跑，未知分支仍先探索再安排，不要求提前写完整模块脚本。

保存失败返回 pending_save；断言差异或动作结果不明停止当前计划并返回具体位置，其他独立计划不受影响。`resource_wait.end_turn=true` 时结束本次自动执行，不轮询、重领或改变请求 ID 重放；明确修正后复用原 plan_id 续接，原动作账本返回已完成结果。每条结果含 elapsed_seconds/save_seconds，可直接核对正常业务执行耗时，不另开性能测试。旧执行机不支持此入口时保留原单步/兼容批次，不热升级活动租约。
