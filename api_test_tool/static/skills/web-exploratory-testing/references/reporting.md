# 用例、证据与报告表达

## 用例名称先说明验证点

用例名称（UI 的 `scenario`、API 的 `title`）按 **场景／操作 → 预期行为** 写成自然中文短句，箭头不必写进标题。读者只看名称就应知道测什么；名称描述预期，不代表已经通过。每条围绕一个独立业务判断：翻译完整性、术语准确性、原职位标识保留分别设计；端到端链路保留业务终点，不按每次点击拆分。

| 字段 | 应写内容 |
| --- | --- |
| 名称 | 具体条件或动作，以及要验证的行为；如“点击中文翻译后，职位简介、职责和任职要求均有对应译文” |
| 前置条件 | 测试开始前的业务状态和必要依赖，如“该英文职位尚未生成中文译文” |
| 测试数据 | 实际对象名称、用于定位的 ID、完整输入或文件；能看出每项数据的用途 |
| 测试步骤 | 真实入口、控件、输入、等待和观察位置，按编号写出可独立复现的操作 |
| 预期结果 | 与当前验证点对应的可观察结果和通过判据，如哪些章节须有译文；规则未知则明确待确认 |

公共登录、入口确认、样本准备归入准备说明或用例前置/步骤，不单独当作业务功能覆盖。登录或入口本身在测试范围内时，仍保留其独立规则用例。执行纪律（如不得伪造状态、需先核对样本）放在执行规范，不逐条复制到前置条件。共享准备可复用，具体用例仍须能独立复现，不用“同上”替代真实入口和输入。

保存前做一次文本一致性核对：名称、测试数据、步骤、预期引用同一业务对象，职位名、ID、文件、输入值对应一致；有意比较不同对象时说明各自作用。样本未知标待准备或待核对，不猜造对象来填空。仅调整表达不能修改已有测试目标、执行事实、结果或证据，也不能为简短删掉完整输入和复现路径。

以下只示范写法，实际预期须有本轮需求依据：
- “英文完整详情首次展示原文和主动翻译入口” → “未翻译的英文职位首次打开时，展示英文原文和翻译按钮”。
- “主动翻译真实英文JD并逐段核对全文” → “点击中文翻译后，职位简介、职责和任职要求均有对应译文”；术语准确性另列。
- “英文职位中文参考名和原身份保留” → “翻译后显示中文参考职位名，并保留原英文职位名及职位标识”。

## 截图只留能说明当前问题的证据

先明确图片需要证明的事实，再选当前可见画面。默认保留问题控件、对象标题/页面位置及必要上下文；局部特写仅补充，不单独替代上下文。跨步骤差异可组合已保存输入记录与结果图；确需两个画面才分别取证，不固定每例张数，不默认截整张长页面。

关键结果或缺陷仍在时取证，在刷新、切换或恢复前保存原 case_id、step 和实际 captured_at。截后就地看一次同一张图片，核对关键文字、遮挡、当前用例和对象；这只是看图，不重复操作、查询或验证业务。已有证据足够就复用；明显漏掉关键内容且现场还在时才针对缺口补截，不循环截图，不为补图重跑业务。现场丢失或截图失败如实写证据缺口，继续其他场景，不拿无关图充数。

原生直接 Playwright 可用随包 nativeCaptureEvidence({page,case_id,step,directory,preview})：只截一次当前视口，preview 展示同一份图片字节供当前回合核对，不另截图；返回 assets 可沿原 asset_files 保存。确需特写才传 detail 定位器。生成文件不代表语义核对完成，不新增服务端发布门槛、截图数量要求或自动模型调用。原生其他浏览器使用其公开截图 API，保留相同取证原则。

## 步骤写实际动作，让别人能直接复现

每条包含中文名称、规则依据、方法/维度、前置条件、完整输入、编号步骤、预期、实测、状态、证据、缺陷与复测情况。相关内容可合并单元格描述，避免无意义字段撑宽表格。

- 步骤写明网址/入口、点击的页面文字、逐次输入原文、顺序、等待完成标志、观察位置和具体核对值。
- 多轮对话分开写每轮发送内容，说明保持同一对话或新建独立对话；不能让读者一次发送整段多轮文本。
- 前置数据给中文名称、完整内容及建立方法；历史对象给可用入口和重建方法，不能只丢线程ID。
- 一个触发条件可以独立通过或失败时应单独成例。例如空文件、扩展名不支持、内容损坏分别使用独立用例和实体文件，不能因都属于“上传异常”就挤在一条里。不同初态、边界值、权限及错误结果分别使用独立 case_id；共享资料、步骤或证据不改变粒度，同一场景的连续断言保留在该例检查点中。
- AI 能安全生成的测试数据必须在执行前真实生成并核验，不能只写文件名或描述后标未执行。文本输入完整保存在 test_data；文件、图片、音视频等实体数据作为 fixture 关联到对应报告用例，使用户能直接查看或下载。使用 case_id、step 显式关联原用例，并为读者写明文件和实际用途；正确的共享资料可分别关联多条用例，不能机械挂给无关用例。关联是否合理由 Codex 核对，平台不以文件名是否出现在文案中拦截上传或发布。确实需要人工提供的专有设备/账号/真实介质才标人工，并写明缺少条件。
- 禁止“输入相关信息”“执行某类型测试”“同上”“参考某编号”代替操作。编号仅用于追踪，不能成为唯一定位方式。
- 原始记录没保留某一步就承认缺失；新编步骤标待复测，不能冒充过去执行过。
- 每个失败用例同处包含缺陷标题、触发条件、影响、预期与实测差异、复现次数及证据，不另找缺陷报告。
- 交付前模拟陌生读者，仅按文档检查入口、输入、操作和判断是否足够；已有同轮、同对象、同条件的明确初态与结果证据直接复用，不因整理缺陷再次执行业务。只在具体证据不足、条件变化或用户/原用例明确要求时补核对应缺口。

测试报告是给人看的。用例名称直接说要验证什么；测试数据先列文件名、实际大小和必要输入，脚本名、哈希与记录 ID 只在复核确有需要时补充。步骤用日常中文写操作与观察位置，不写“按包含关系验证”“完整确定性生成器”等内部设计术语。“沿用已登录账号”只能是前置补充，不能作为测试步骤；必须写入口 URL、登录状态确认方式、控件/对象、等待状态和观察位置，选择/刷新/核对分开编号。整理失败用例、缺陷或更正历史步骤时，阅读 [可独立复现的缺陷步骤](defect-reproduction.md)，依据真实记录补齐入口、具体动作、输入、等待状态和故障触发点；不能把用例设计摘要直接当作缺陷复现步骤。`expected`、`actual`、`conclusion` 的第一句话分别给出预期、观察事实和本用例结论，再补错误码与证据；不把推测写成事实。

缺陷正文只增加“AI 解读”和“建议优化”两部分：ai_analysis 说明现象、影响及原因，区分现场事实、已核实的代码或日志依据、推测与未验证边界，根因未查明时明确说明，不另设原因分析栏目；recommendation 按条写针对该问题的修复方向、交互改进和回归关注点，不能把建议当成已实现或已验证。两项均为文本，随描述展示、复制并供人工审核后提交 PingCode，不新增生成按钮或自动模型调用；不为补分析擅自扩大测试或排查范围。

保存平台用例时，同步写一段 `ai_analysis` 供报告直接展示。读者不需要懂测试或开发术语：用几句日常中文先说具体功能哪里成功或失败、对使用有什么影响，再说明已确认的事实和仍未验证的部分。不要只换成中文术语或复述步骤。失败发生在哪一步不等于已经找到原因；没有证据确认根因时，直说“具体原因还没查明”，不能把猜测写成结论。未执行、阻塞、验证未完成要明确尚未验证的功能，不能暗示已经通过或已经失败。

不要用“夹具、断言、召回、注入、提交链路”等内部术语、工具名或用例编号代替解释。必要的技术信息留在详细记录，不改动实际使用的输入、错误码、测试状态、判断标准和证据。执行结果变化时同步改写解读；关联其他用例时先解释它验证了什么，只有已读取真实结果才能写恢复结论。篇幅以读者能理解为准，不为压缩字数删掉业务影响或不确定性，也不强制套固定栏目。

例如，把“夹具格式已由 pypdf 验证有效单页；故障发生于解析服务提交阶段，而非内容断言”写成：“文件格式检查通过，但平台在提交解析任务时失败，后面的搜索和问答没能继续验证。提交失败的具体原因还没查明。”把“32 MiB 边界断言通过，后续解析失败”写成：“32 MiB 文件被成功接收，大小限制这一项通过了。但文件解析失败，不能据此说它已经能用于知识库问答。”这些是表达示例，不是预设测试结果；只采用当前证据支持的内容。

判定前先写清本用例的成功标准和业务终点。文件进入服务器、创建记录、解析成功、建索引及可以检索是不同阶段。若用例只验证 32 MiB 文件是否通过大小校验，接收成功可记通过，但必须在实际结果和结论中直说“解析失败，文档不可用于检索”；若用例验证文档进入知识库并可用，解析或检索失败就不能记通过。HTTP 成功码、绿色提示和记录创建都不能替代业务终点。规则确实不明时用一句话写明待确认的具体规则，例如页面“32 MB”按 1000 还是 1024 进制计算。

不能在执行后偷换用例目标来保留“通过”。批量上传用例只顺序上传了单个文件、文件下载一致性用例只看了引用原文、端到端用例只保存了配置而没有验证业务召回，都不算原目标通过。已完成一部分就标“验证未完成”并写清未完成的步骤；原目标根本没有入口则标“未执行”或“不支持”并说明。若另设更窄的用例验证局部能力，标题和结论必须写明范围，同时关联后续失败用例。

示例：打开指定网址并登录测试角色→点击“新的对话”→输入完整语句“请长期保存：以后所有岗位默认用中文沟通。”并发送→等待“本轮处理已完成”→新建独立对话发送“我保存的默认沟通语言是什么？只查询长期偏好。”→分别核对保存确认、实际处理步骤和新对话回答是否为中文。实际交付需拆成编号步骤并写入真实网址。

# 证据撤下

误存了不应交付的证据时，使用正式 `withdraw_ui_test_asset`，传入原 project_id、execution_id、case_id、asset_id、sha256、简短非敏感 reason 和稳定 request_id。原字节、元信息和审计保留，报告、导出与下载不再提供该资产；用例事实、结论与保存修订不变。未知响应仅用同一 request_id 和完全相同参数核对原回执，不删除文件、修改原图、复制记录或重跑业务。撤下不自动发布报告；确认成功后沿原报告流程收尾。
