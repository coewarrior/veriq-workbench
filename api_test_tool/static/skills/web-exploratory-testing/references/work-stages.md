# 共同前置与原节点阶段安排
## 当前平台全局范围（2026-10-26）

当前平台全局范围：多账号、双账号、跨账号及跨租户对照/隔离业务场景一律不测（用户明确排除多账号场景）。保留具体设计和已有真实结果；未执行项使用 not_run，not_run_reason 填写上述原因；UI cases.account_scope、API design.account_scope 使用 multi_account/cross_account/cross_tenant 明确范围。不算通过，不申请第二账号、不等待账号集合、不为其创建执行会话或续接，不另做替代测试。普通继续测试/重测不解除此规则。不同模块各用一个账号并发仍允许；单账号权限、匿名及其他适用风险覆盖保持。已有真实对象责任的必要清理和无需账号的报告仍按原授权及回收协议处理，不扩展业务测试。

此明确范围变更优先于下文历史多账号示例；既有隔离、授权、清理及回收协议仍保护历史现场，不授权发起新多账号业务。


本安排改变资源等待方式，不改变测试范围、独立用例粒度、持续探索或结果判定。每模块仍为一个原节点、一个原执行聊天；不复制队列资历，不减少并发。

共同前置分两次嵌入已有准备：派发/领取前，复用本轮资料及账号清单核对目标、所属账号项目、已知样本与观察通道；登录后首次实际页面侦察，立即核实必须进 UI 才能确认的租户、角色、样本状态和入口。不要等具体用例失败后才回头查共同条件。前者不产生凭假设设计的用例，后者仍遵循实际侦察后保存首版具体设计；无统一审批屏障，不新增逐条预检或重复读整份历史。

开始依赖该条件的业务前，核实账号/租户/角色、样本及状态、目标入口、结果观察通道。授权内可准备的先准备。共同条件沿原 cases.dependencies 和 record_ui_dependency_check 保存一次，关联确实受影响的独立 case_id；账号或状态不同的条件填写非秘密 account_id / state_ref，不能把 A 账号成功当成 B 就绪。未知、未准备和已验证缺失分别记录；blocked 是依赖诊断，由 Codex 判断实际受影响分支并继续其他可执行用例，不自动改判或阻断资源候选。条件变化后再核实，不逐动作重复预检。

实际页面侦察和首版具体用例保存后，用原执行包 `input={action:"work_plan",plan_file:绝对路径}`（CLI `native-work-plan --binding-file ... --plan-file ...`）登记阶段。JSON 为 `{"units":[...]}`，项目和执行 ID 从原 binding 取得。每阶段包含稳定 id、原 case_ids 或 checkpoint_refs:[{case_id,checkpoint_id}]、完整 requires、真实阶段依赖 depends_on，可选原现场引用 resume_ref。

requires 明确 phase:"exploration"|"execution"、account_ids 或完整 requirements:[{target,environment,tenant,role}]、适用 locks。指定账号默认 required，确实依赖原账号对象、租户、角色或原现场的阶段保留硬绑定。普通可替换单账号阶段：用例与 requires 均明确 account_scope:"single_account"，requires.account_selection:"preferred"，account_ids 可为一个历史偏好或 []，requirements:[]；这明确授权原项目、目标内选择一个合格账号，不要求编造未知租户/角色，也不把上次账号误当必选。原角色、租户确有要求时仍填写完整 requirements；cleanup 或 resume_ref 原现场不使用上述可替换声明。只有真实独立可替换的场景可这样声明，不为换号重跑已完成结果。未知场景不能假定一个账号够用。共同初态可同批安排，独立场景仍保留独立 case_id；同一断言不放进多个阶段。

阶段的 depends_on 表示明确的先后顺序，服务端以所引用前置阶段已完成（passed 或 failed）推进，不要求业务通过。只需等待某个检查点完成时，将该检查点作为前置单元，不把整个 read/entry 批次的通过作为独立阶段前提。Codex 根据实际结果判断下一步是否可做；已声明 failed 的用例不因此自动重做。业务依赖台账与 checkpoint gaps 只作诊断，不影响资源候选；真实账号、锁、未退出保护仍有效。发现顺序误建时按真实事实修正同一计划，不为消除身份或资源冲突删减约束。

账号存在不代表属于当前模块的账号项目或目标入口。管理后台账号与业务端账号分属项目时，先沿现有平台项目绑定/相应目标入口安排其获准范围；不能把别项目账号硬塞进当前 work_plan，也不能编造 prod/HR 等未核实元数据。需要保持原模块范围和独立报告归属，配置缺口明确交原协调者，不归为被测业务失败。

例如原用例 A1/A2 只需当前账号，AB1 真实需要两个账号：只安排 single 引用 A1/A2；AB1 保留具体设计并标记不测，不创建 cross 阶段、不申请第二账号。不让整个模块提前持有未来所有账号。新分支先追加原轮具体用例，再扩充同一阶段计划；保留旧阶段 ID、原顺序和全部结果，不把首版计划当范围上限。只在首次、设计实质扩充或资源边界保存计划，普通结果保存不另写计划。

到资源边界使用 `input={action:"work",unit_id:"原阶段ID"}`（CLI native-work-boundary），通过服务器计划版本和完整资源摘要申请，不手工删减锁；多账号业务应标不测，不删掉第二账号后冒充单账号验证。

- excluded=true / next_action=skip_excluded_scenario：记为不测，不准备浏览器、不等待资源、不为此续接，继续其他获准单账号用例。
- next_action=continue_current_work：继续回执列出的原用例/检查点；缺资源分支留在原阶段，不循环等待或重跑已完成项。
- 原租约已获所需资源：沿原现场执行对应阶段。探索共享权限不能执行需要独占的动作。
- release_required=true：核对原未知操作及现场保留规则，真实关闭本任务浏览器，再用 `input={action:"yield",from_observation:true}` 临时交还；保留原记录和顺位，不能用 completed/release 冒充临时交还。
- 资源需保留或存在未知写入：处理回执指明的原问题，不自动释放、重复登录/提交或改判业务失败。

等待时保存原进度并结束本回合，原模块与未完成阶段仍在队列；这是临时 yield，不是模块 completed。“测不了跳过/不询问”仅跳过已核实不能执行的业务分支，不取消正常资源续接。收到原资源事件先用周期入口 `input={action:"resume",notification:原通知.claim_arguments}`，或 CLI `native-resume --assignment-file 原文件 --directory 原目录 --notification-file 通知文件`。入口机械核对原身份、兼容内外层 work_token，并做一次阶段预检；只有 stage_ready=true 才按回执完整账号数准备环境和原 prepare --resume，不再另查一次 stage_ready/context，不手抄参数。通知不是占号，竞争失败保留原节点；旧令牌、停止或已完成阶段不能重放。不热替换旧轮执行包。

领取/准备中断使用原目录和 resume，读原绑定/租约/基线，不重建基线。完整私有控制回执是依据，终端警告或截断不代表请求失败；缺失回执保持未知，不自动重发。正常新输入打断先处理用户指令，不记工具故障。

模块实际执行结束才用原 release（先交还、报告待补）或 closeout。报告差量修正与发布沿原 binding，无需重新占号，不重跑业务或重抄结果。一次核对原范围、具体遗漏及真实缺口，只有实质变化才保存。格式校验一次列出问题，不改实际结论迎合格式；未知保存仅凭原请求、原载荷、原绑定及精确修订确认。
# 结束后阶段与清理补充

原排队不变。阶段登记、正式续接、清理 404 与未知核实按 [execution-recovery.md](execution-recovery.md)；不要向已结束租约发 checkpoint，也不把模块工作委托给其他账号持有者。
